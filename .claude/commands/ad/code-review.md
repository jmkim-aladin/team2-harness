# GitHub PR 코드 리뷰

팀 하네스 기준으로 GitHub PR을 리뷰하고, 사용자가 미리보기를 승인하면 리뷰를 게시한다. 판정 기준의 SoT는 [code-review-policy](../../../policies/code-review-policy.md)이고, 이 문서는 적용 시점과 절차를 담는다.

## 리뷰 범위 — 변경 영역에 한정한다 (최우선)

<!-- canonical:code-review-scope targets=.codex/skills/ad-code-review/SKILL.md -->
아래 규칙은 이 문서의 다른 모든 절차보다 우선한다. 범위를 넘긴 리뷰는 작성자 시간을 쓰게 만들고, PR과 무관한 논쟁으로 머지를 지연시킨다.

- 판정 대상은 **diff hunk에 실제로 포함된 줄**, 그리고 그 줄이 깨뜨리는 기존 동작이다
- diff 밖 파일·기존 코드의 결함은 **지적 대상이 아니다** — 문맥으로 읽었어도 마찬가지. 눈에 띄면 미리보기에 `PR 밖 관찰` 한 줄로만 남기고 게시 본문에는 넣지 않는다
- **확대해석 금지**: diff에 없는 의도·설계 계획·후속 작업을 추정해 지적하지 않는다. 스펙 축 근거는 티켓·설계 문서에 **명시된 것**뿐이다
- 추정이 남으면 지적이 아니라 3단계 `확인 못 한 것` 또는 질의 코멘트다
- "이렇게 했으면 더 좋았다"류 대안 제시는 diff가 실제로 깨는 것을 지목할 때만 코멘트가 된다
- **릴리스 묶음 PR**(원 PR 증거가 있는 stage·prod 배포 PR. 브랜치 이름만으로는 판정하지 않는다)은 판정 대상이 바뀐다: 원 PR에서 이미 리뷰된 hunk는 재판정하지 않고, 릴리스 전용 변경과 묶음 구성(누락·혼입·교차 영향·환경값·선행 의존·base 드리프트)을 판정한다 — 1단계 «릴리스 묶음 후보»
<!-- /canonical:code-review-scope -->

## 사용법

```
/ad:code-review {PR번호 | URL | owner/repo#N}
/ad:code-review 123 --no-cross   # 교차 모델 검증 생략 요청 (--no-codex 동일). 위험 신호가 있으면 무시된다
/ad:code-review 123 --full       # 릴리스 묶음 후보도 전체 diff를 일반 리뷰로 판정
```

준비: `gh --version`·`gh auth status` (없으면 `brew install gh`·`gh auth login`). YouTrack 티켓·KB 조회 인증은 [youtrack/api-guide.md](../../../youtrack/api-guide.md). 읽기 명령은 `.claude/settings.local.json`의 `gh pr view` 계열 허용 목록으로 통과하고, 게시는 7단계 게이트를 거친다.

## 조건부 참조 — 조건이 맞을 때만 읽는다

| 파일 | 읽는 때 | 읽지 않는 때 |
|---|---|---|
| [preview.md](../../../docs/code-review/preview.md) | 3단계 이해 브리핑을 쓰기 시작할 때 (미리보기·게시 코멘트 규격) | Draft 스킵처럼 미리보기 전에 끝날 때 |
| [release-bundle.md](../../../docs/code-review/release-bundle.md) | 1단계 릴리스 묶음 후보이고 `--full`이 없을 때 | 후보가 아니거나 `--full` |
| [cross-model.md](../../../docs/code-review/cross-model.md) | 5단계에서 교차 모델을 실제로 실행할 때 | 생략이 확정됐을 때 |
| [publish.md](../../../docs/code-review/publish.md) | 7단계 사용자가 게시를 승인한 뒤 | 승인 전 |

## 검증 순서

[hypothesis-verification-order](../../../policies/hypothesis-verification-order.md)를 적용한다 — "이거 맞나요?"류 질의를 달기 전에 콜그래프/grep + dev DB 읽기 쿼리로 답이 나오는지 먼저 확인하고, 잔여 의문만 작성자에게 묻는다. dev DB 읽기는 사전 동의 ([local-credentials-policy](../../../policies/local-credentials-policy.md)).

공유 상태·비동기 순서·외부 라이브러리·직렬화/외부 계약의 가정이 안전성을 좌우하면: 핵심 가정을 한 문장으로 적고, 실제 고정 버전·호출 경로·소비자를 확인하고, 가장 작은 재실행 가능한 검사로 확인한다. 해당 축 근거에 가정·근거 수준(정적 확인/실행 확인/미확인)·관찰값 위치를 남긴다 — 정적 근거만 있으면 실행 검증으로 보고하지 않고, 별도 전체 위험표는 만들지 않는다.

실행 수단이 없다는 이유만으로 새 승인 차단 조건을 만들지 않는다. 근거가 부족하면 기존 미확인 축·이벤트 규칙(§이벤트와 승인 조건)을 적용하고, DB·운영 쓰기 권한은 확대하지 않는다.

## 리뷰 축 — 기본 2축 + 조건부 운영 축

이해 패스(3단계)를 통과한 뒤 축마다 따로 판정·보고하고 병합·재순위하지 않는다 — 한 축 통과가 다른 축 실패를 가리는 것을 막는다.

- **기준 축**: 팀 정책·컨벤션·코드 스멜. 문서화된 기준 위반(하드)과 판단성 스멜을 구분하고 근거 문서를 인용한다. 저장소가 명시적으로 쓰는 패턴이 일반 스멜 기준보다 우선하고, 린터·CI가 잡는 항목은 재검토하지 않는다
- **스펙 축**: 티켓(5W1H)·설계 문서 대비 요구 누락/부분 구현, 요청 밖 변경, 의도와 다른 구현. 연결된 티켓/스펙이 없으면 `생략 — 연결 스펙 없음`, 연결된 스펙을 읽지 못했으면 `미확인`이다
- **운영 축 (조건부)**: 배치·정산·외부 연동·레거시 SP 경로를 건드릴 때만 — 재실행 가능성, 멱등성, 부분 실패 복구, 외부 타임아웃, 실패 건 운영자 식별, 정산 데이터 영향. 해당 없으면 생략하고 명시한다
- **발견 보고는 커버리지 우선**: 불확실·저심각도 발견도 신뢰도·심각도를 병기해 보고하고 채택은 판정에서 거른다 — 발견 단계 자기 필터링은 recall을 떨어뜨린다. 변경 영역 안에서만 적용하며 범위를 넓히는 근거가 아니다

## 실행 지침

### 0. 입력 파싱

- 대상 레포를 명시한다: `gh pr`에는 `--repo {owner}/{repo}`, `gh api`에는 `repos/{owner}/{repo}/...` endpoint — 근거: 하네스 cwd(`team2`)는 대상 레포가 아니라서 누락 시 현재 remote를 따라가 엉뚱한 레포를 조회한다
- URL은 `{owner}/{repo}`·`{N}`을 추출한다. 숫자만 오면 `catalog/*.yaml`의 `repos:`에서 후보를 모아 `AskUserQuestion`으로 고르고, `{owner}/{repo}#{N}`·`{repo}#{N}`도 같은 방식으로 해석한다. 추론이 안 되면 묻는다
- 1단계 조회 직후 첫 출력으로 한 줄 노출한다 — 매핑·머지 방향이 틀리면 조기 중단할 수 있게: `대상: AladinCommunication/max-front #1308 (feature/DEV2-1234 → develop) · 작성자: 안혜련(00HyeRyun00)`

### 1. PR 정보 수집

```bash
gh pr view {N} --repo {owner}/{repo} --json title,body,author,baseRefName,headRefName,baseRefOid,headRefOid,commits,files,additions,deletions,isDraft
```

**Draft**: `isDraft`가 `true`면 여기서 `PR #{N}은 Draft 상태 — 리뷰 스킵` 한 줄로 종료한다 — 작성자가 완료 신호를 주지 않았으므로 diff도 받지 않는다. 사용자가 Draft임을 알고 명시적으로 요청할 때만 진행한다. 아니면 나머지를 수집한다:

```bash
gh pr diff {N} --repo {owner}/{repo} --name-only
rtk proxy gh pr diff {N} --repo {owner}/{repo} > {스크래치}/pr{N}.diff
# 앞선 리뷰 라운드: 인라인 코멘트 · 리뷰 본문 · 일반 코멘트
gh api repos/{owner}/{repo}/pulls/{N}/comments --jq '.[] | "--- \(.id) \(.user.login) \(.path):\(.line) reply_to=\(.in_reply_to_id)\n\(.body)\n"'
gh api repos/{owner}/{repo}/pulls/{N}/reviews --jq '.[] | "--- \(.user.login) \(.state)\n\(.body)\n"'
gh api repos/{owner}/{repo}/issues/{N}/comments --jq '.[] | "--- \(.user.login)\n\(.body)\n"'
```

- **리뷰 리비전 고정**: 조회한 `headRefOid`·`baseRefOid`를 이후 비교·원본 링크·교차 모델·게시 `commit_id`에 쓴다 — 브랜치 이름은 머지·푸시로 움직인다
- **diff 누락 검출**: 전체 diff는 `rtk proxy`로 파일에 받고 `Read`로 절 단위 소비한다. 받은 직후 `grep -c '^diff --git' {파일}`이 `--name-only` 파일 수와 같은지 센다. `gh api ... contents`로 원본을 받을 때도 `rtk proxy`를 붙인다. 근거: rtk 훅이 diff 본문을 버리고 `--name-only`는 온전히 통과해 빈 diff 위에서 조용히 리뷰가 진행된다 (2026-08-10 PR #27: 1688줄→518줄, `diff --git` 0건)
- **앞선 라운드 선독**: diff보다 먼저 세 조회를 모두 읽는다 — 나 자신이 남긴 것도 세션이 다르면 컨텍스트에 없다. 작성자 답변이 달린 항목은 새 코멘트로 다시 올리지 않고 4단계 판정 입력으로 쓰며, 해소되지 않은 부분만 그 스레드의 답글로 남긴다. 답변이 diff 밖 사실(레포 밖 파일·운영 DB·배포 계획)을 근거로 들면 검증 순서대로 확인해 근거 수준(정적 확인/실행 확인) 그대로 미리보기에 남긴다. 근거: 2026-09-22 Tobe PR #205 — 1라운드에서 답변된 질문을 새 세션이 재게시해 삭제로 되돌렸다
- **릴리스 묶음 후보**: base가 `deploy/*`·`master`·`main`·`release/{YYYY.M.N}`이고 `--full`이 없으면 [release-bundle.md](../../../docs/code-review/release-bundle.md)로 원 PR을 추적해 묶음 모드 여부를 가린다 — 브랜치 이름만으로는 묶음 판정하지 않는다. 후보가 아니면 일반 리뷰다

### 2. 서비스 컨텍스트

대상 레포의 서비스를 `catalog/*.yaml`에서 확인한다 — 이해 패스 배경과 판정 기준이 여기서 나온다: 기술 스택·아키텍처 패턴, 레거시면 LEGACY_BOUNDARY.md 위반 여부, 현대화 트랙(Observe/Wrap/Extract) 방향.

### 3. 이해 패스 — 판정 전에 변경을 이해한다

판정하지 않는 단계다 — 이해 없이 4단계로 가면 추측 리뷰가 된다. 섹션은 [`/ad:explain`](./explain.md)의 5개(한 줄·배경 2층·직관·변경점 묶음·확인 못 한 것)와 검토 집중점이고, 구성·상한·코드 발췌·도식 규격은 [preview.md](../../../docs/code-review/preview.md) §이해 브리핑을 따른다.

- 퀴즈·정답표·HTML 렌더·md 저장·mermaid는 쓰지 않는다 — 읽음을 확인할 독자가 없고 터미널에서 그려지지 않는다. `tools/render_explain_report.py`는 퀴즈를 필수로 검증하므로 돌리지 않는다
- 릴리스 묶음 모드: 변경점을 원 PR 단위로 나누고, 재판정하지 않는 원 PR은 `#{M} · 티켓 · 파일 목록` 한 줄만 적는다
- **경계**: "문제 같다"는 결론 없이 4단계 입력으로 넘긴다. finding·심각도·이벤트는 4·6단계의 몫이다
- **게이트**: 근거(`파일:심볼`·쿼리·문서)를 못 댄 변경 묶음이 남으면 해소하거나 그 항목을 결과에 명시한 뒤 넘긴다. 근거: 근거 없는 이해 위에서 내린 판정은 추측과 구분되지 않는다

### 4. 판정

- 체크포인트는 [code-review-policy](../../../policies/code-review-policy.md) §리뷰 체크포인트·§서비스별 DB/SP 체크 적용·§DB/SP 변경 추가 리뷰 항목을 그대로 적용한다 — 검증 증거·기능 플래그·롤백·DB/SP 첨부물 단계 구분의 기준은 거기 한 곳에 있다
- **지적하지 않는 것** — 팀 관행이다: PR/브랜치 feature ID와 커밋 task ID 불일치, PR 본문의 템플릿 형식 준수(템플릿은 초안)
- **통과도 근거를 댄다**: 축마다 무엇을 봐서 통과인지 `파일:심볼`·테스트명·쿼리로 적는다. 못 대면 `미확인`, 체크 대상에서 제외한 항목은 `해당없음 — 사유`다. 근거는 diff 줄과 그 직접 호출부까지만 찾는다 — 통과 근거를 대려고 레포 전체를 훑지 않는다. 이유: ❌에만 근거를 요구하면 못 본 것과 봐서 괜찮은 것이 구분되지 않는다
- **`왜` 한 줄**: 발견마다 이 변경 맥락에서 어떻게 깨지는지를 이해 패스의 변경점을 근거로 한 줄 쓴다. `null 체크 없음`·`예외 처리 미흡` 같은 일반론은 `왜`가 아니다. 못 쓰면 버리지 않고 신뢰도를 낮춰 질의 코멘트로 강등한다 — 강등은 승인 조건에 걸린다(§이벤트와 승인 조건)

### 5. 교차 모델 검증 (기본 실행)

호스트와 **다른 모델**의 독립 리뷰를 4단계 판정과 대조한다. 호스트 finding은 보여주지 않는다 — 확증편향으로 대조 가치가 사라진다. 같은 모델 자기검증은 대조가 아니다.

| 호스트 | 교차 모델 | CLI 없을 때 |
|---|---|---|
| Claude Code | Codex CLI (`codex`) | 생략하고 명시 (`npm install -g @openai/codex`) |
| Codex | Claude Code CLI (`claude`) | 생략하고 명시 (https://claude.com/claude-code) |

- **발동**: 판정 이벤트와 무관하게 실행한다 — 리뷰당 5분 내외가 들지만 오판을 되돌리는 비용이 더 크다. `--no-cross`(`--no-codex`)면 생략하되, 아래 위험 신호가 하나라도 있으면 실행한다. CLI가 없으면 생략한다
- **위험 신호**: DB 스키마·SP 변경·마이그레이션 / 외부 연동의 호출 추가·계약·타임아웃·재시도 변경 / 인증·권한·회원 식별·결제·정산·구독 경로([common-service-policy](../../../policies/common-service-policy.md) registry 히트 포함) / 레거시 경계 통과(`LEGACY_BOUNDARY.md`) / 테스트 없는 로직 변경 / 순삭제 100줄 초과
- 대상 레포가 팀 소유가 아니면 실행 전 사용자에게 확인한다 — diff가 다른 벤더 모델로 간다
- 릴리스 묶음 모드는 재판정 대상만 보낸다 ([release-bundle.md](../../../docs/code-review/release-bundle.md) §교차 검증). 재판정 대상 0의 승인 취급은 §이벤트와 승인 조건
- 실행이든 생략이든 결과에 한 줄 노출한다 — 조용히 건너뛰면 돌았는지 알 수 없다. 예: `교차검증: 생략 — 사용자 --no-cross, 위험 신호 없음`
- 실행하면 [cross-model.md](../../../docs/code-review/cross-model.md)를 읽고 그대로 따른다 — 클론·SHA 확인, 격리, 읽기 전용, 프롬프트 데이터 경계, 중단·재시도 한계가 거기 있다

**대조**:

| 분류 | 처리 |
|---|---|
| 양쪽 일치 | 신뢰도 상향. 코멘트로 간다 |
| 호스트만 | 유지한다. `왜` 한 줄이 서면 교차 모델이 놓친 것이다 |
| 교차 모델만 | 자동 게시하지 않는다 — 미리보기 별도 블록에 두고 채택은 사용자가 정한다. 채택하면 `왜`를 호스트가 직접 검증해 쓴다 |
| 어느 쪽이든 diff 밖 | 코멘트 후보에서 빼고 `PR 밖 관찰`로만 남긴다 |

교차 모델 출력은 참고 입력이다 — 팀 정책·티켓 문맥이 없어 기준·스펙 축 판정 권한이 없고, `[P1]`이 나와도 이벤트를 자동으로 `REQUEST_CHANGES`로 바꾸지 않는다. 이벤트는 4단계 판정과 사용자가 정한다.

### 6. 미리보기

[preview.md](../../../docs/code-review/preview.md) 규격으로 이해 브리핑·리뷰 결과·쉬운 요약을 메시지 본문 마크다운으로 출력하고 `→ 이대로 게시할까요?`로 끝낸다.

- **로컬 전용** — 게시 본문에 넣지 않는다: 이해 브리핑, 하네스 체크리스트, 교차 모델 대조 결과와 모델 이름, `PR 밖 관찰`, 승인 조건 숫자, 축·신뢰도·심각도 표기, 쉬운 요약
- **로컬 하네스 정보 노출 금지** — PR 독자는 하네스 없이 읽으므로 내부 경로는 근거가 아니라 소음이다: `policies/*.md` 같은 경로·정책 문서명은 "팀 코드리뷰 정책"·"서비스 카탈로그"로 일반화하고, 하네스 갱신 제안은 게시 본문엔 "하네스 갱신 필요"까지만, 구체 경로는 미리보기에만 둔다

### 7. 사용자 승인 후 게시

사용자가 미리보기를 검토하고 "이대로 게시"라고 답했을 때만 게시한다 — 권한 모드와 무관하게 지킨다. 교차 모델만 발견한 항목은 사용자가 채택한 것만 들어간다. 승인 후 [publish.md](../../../docs/code-review/publish.md)를 읽고 실행한다. 인라인 코멘트는 JSON 페이로드로 한 번에 보낸다 — 근거: 2026-05-27 `gh api -f 'comments[][...]'` 폼 인코딩이 `side`·배열 인덱스를 잘못 매핑해 422로 실패했다.

## 이벤트와 승인 조건

| 이벤트 | 기준 |
|---|---|
| `REQUEST_CHANGES` | 확인된 차단 이슈: 보안, 버그, 레거시 경계 위반, 복구할 수 없는 데이터 손실. 배포 첨부물(롤백 스크립트 등) 누락은 차단 사유가 아니다 |
| `APPROVE` | 이슈 없음 또는 비차단 제안만(스타일·선택적 개선) — 아래 승인 조건 3개를 모두 만족할 때만 |
| `COMMENT` | 중립 피드백·질문·확인 요청. 승인 조건을 못 채운 경우도 여기로 내린다 |

우선순위는 표 순서다 — 확인된 차단 이슈가 있으면 승인 조건과 무관하게 `REQUEST_CHANGES`이고, "못 채우면 `COMMENT`"는 `APPROVE` 후보에만 적용한다.

`APPROVE` 승인 조건 — 하나라도 못 채우면 `COMMENT`:

1. **미확인 축 0개** — 축마다 통과 근거를 댔다
2. **강등된 질의 항목 0개** — `왜`를 못 써서 질의로 내린 항목이 없다. "문제일 수 있는데 확인 못 했다"는 승인이 아니다 — 이 조건이 없으면 강등이 승인을 만드는 통로가 된다
3. **교차 모델 검증 완료** — 셋 중 하나:
   - **정상 완료**: exit 0 + 유효한 최종 판정(`[P1]`/`[P2]` 발견, 또는 검토 범위·결론을 적은 `[NONE]`). 판정 계약은 [cross-model.md](../../../docs/code-review/cross-model.md)
   - 위험 신호가 없고 사용자가 `--no-cross`를 명시했다
   - 릴리스 묶음 재판정 대상 0이고, 원 PR 전부의 교차검증 정상 완료 근거를 확인해 미리보기에 위치를 적었다 — 원 PR `APPROVED`만으로 추정하지 않는다

   빈·중단·실패 출력, CLI 없음, 타임아웃, 근거 없는 원 PR 재사용은 미충족이다 — 생략 사유를 노출하고 `COMMENT`로 내린다

세 조건을 미리보기에 숫자로 노출한다 — 오판은 "통과라고 적었지만 실은 안 본 것"에서 나오므로 통과 쪽에도 같은 증거 부담을 둔다. `APPROVE`는 머지 판단이며 출시 준비 완료가 아니다 ([code-review-policy](../../../policies/code-review-policy.md) §리뷰 원칙).
