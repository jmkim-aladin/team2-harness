# 자기 PR 셀프 리뷰 — 완료까지

작성자 본인의 PR을 **다른 에이전트에게 리뷰받고**, 이 세션은 작성자로서 PR 코멘트를 읽어 반영·답글·재리뷰 요청을 `리뷰 완료`까지 반복한다. 판정 기준은 [/ad:code-review](./code-review.md)가 SoT이고, 이 문서는 진행 절차만 담는다.

의도: 작성 세션이 리뷰를 겸하면 자기 맥락을 그대로 믿어 결함을 놓친다. 리뷰어는 PR과 코드만 보는 새 세션이어야 독립성이 생긴다.
근거: 2026-10-13 AASM PR #57·#58 — 별도 세션 리뷰가 작성 세션·교차 모델 리뷰가 놓친 결함(제외 판정 순서, 영구 삭제 원복, 리뷰 반영 커밋이 만든 회귀)을 잡았다.

## 사용법

```
/ad:code-review-self {PR번호 | URL | owner/repo#N}     # 라운드마다 게시·push를 사용자에게 묻는다
/ad:code-review-self 58 --auto                         # 이 PR의 게시·반영 push·답글을 완료까지 위임
/ad:code-review-self 58 --rounds 3                     # 라운드 상한 (기본 5)
```

`--auto`의 위임 범위는 **이 PR 하나**의 리뷰 게시, 리뷰 반영 커밋·push(fast-forward), 스레드 답글까지다. 머지·force push·base 변경·티켓 상태·다른 PR은 위임 밖이라 사용자에게 묻는다 — 사용자 확인 게이트는 invariant이고, 호출 인자로 범위를 밝혀 위임한 것만 대신한다.

## 전제

- PR 작성자 = `gh api user` 로그인. 아니면 `/ad:code-review`로 안내하고 끝낸다 — 남의 PR에는 작성자 반영 단계가 없다
- `HERDR_ENV=1` — 리뷰어 pane이 필요하다. 없으면 다른 세션에서 `/ad:code-review {PR}`를 실행해 달라고 요청하고, 게시 뒤 이 명령을 다시 부르면 3단계(상태 읽기)부터 진행한다
- 수정 작업 폴더는 PR head 브랜치를 체크아웃한 worktree다. 메인 작업 폴더가 다른 브랜치이거나 미커밋 변경이 있으면 별도 worktree를 만든다 — 다른 작업의 변경이 리뷰 반영 커밋에 섞이지 않게 하기 위해
- 상태 파일: 스크래치 `pr{N}-self-review.json` (라운드, 이 세션이 단 답글 ID, 마지막 push SHA). 셀프 PR은 리뷰어와 작성자가 같은 GitHub 계정이라 작성자 표시로는 누가 쓴 코멘트인지 가릴 수 없기 때문

## 진행 — 기본 순서, 상황에 맞게 조정 가능

### 1. 리뷰어 띄우기

[/ad:orchestration](./orchestration.md) 규칙으로 reviewer 역할 Claude peer를 연다 — 모델은 `team2-agent profiles`의 reviewer, 이름 충돌 확인, pane 라벨 `{이슈}/claude1 — PR #{N} 리뷰`.
첫 프롬프트는 슬래시 명령 한 줄 `/ad:code-review {owner/repo#N}`만 보낸다. 앞에 envelope나 작성자 설명을 붙이면 슬래시 명령으로 인식되지 않고, 리뷰어가 작성자 맥락을 받아 독립성이 사라진다.

리뷰어 진행은 Herdr로 본다: `herdr agent prompt {이름} "…" --wait`(백그라운드 실행)로 멈출 때까지 기다리고, 중간 상태는 `herdr agent get`·`herdr agent read --source recent-unwrapped`로 확인한다. Herdr는 **언제 끝났는지**만 알려 주고, 판정 내용은 3단계에서 GitHub으로 읽는다.

완료: 리뷰어가 미리보기를 내고 `이대로 게시할까요?`에서 멈춰 있다(`agent get` idle).

### 2. 게시 승인

`herdr agent read`로 미리보기의 발견 목록과 이벤트를 읽는다.

- 기본 모드: 발견 목록 요약을 사용자에게 보여 주고 게시 여부를 묻는다
- `--auto`: caller가 `이대로 게시`로 답한다

게시 답에는 다음을 붙인다: "자기 PR이라 APPROVE·REQUEST_CHANGES는 GitHub이 거부(422)한다. event는 COMMENT로 하고, 판정은 리뷰 본문 첫 줄에 `리뷰 완료` 또는 `수정 필요`로 적어 달라." 3단계가 GitHub만 읽고 상태를 판정하려면 이 표지가 있어야 한다.

미리보기가 `교차 모델만 발견 — 채택할까요?`를 물으면: 기본 모드는 사용자에게 묻는다. `--auto`는 리뷰어의 호스트 검증이 코드 근거(파일:행)로 성립을 보인 항목만 채택하고, 미확인 항목은 넣지 않는다 — 검증 안 된 지적을 게시하면 작성자 루프가 근거 없는 수정을 만든다.

완료: `gh api repos/{o}/{r}/pulls/{N}/reviews`에 새 리뷰가 보인다.

### 3. 상태 읽기 — GitHub이 SoT

pane 출력이 아니라 PR을 읽는다 — pane은 잘리고 요약되며, 다음 세션은 pane을 볼 수 없다.

- 마지막 push 이후 최신 리뷰 본문의 첫 줄 판정
- 인라인 스레드마다 마지막 코멘트: 상태 파일에 없는 ID면 리뷰어가 남긴 열린 항목이다
- 일반 코멘트(issues comments)

완료: 열린 항목 표(위치·종류 `[중요]`/`[제안]`/`[질문]`·요지)가 있다. 열린 항목 0이고 판정이 `리뷰 완료`면 6단계로 간다.

### 4. 작성자 반영

항목마다 코드에서 근거(파일:행)를 찾아 수용·부분 수용·반박을 정한다. 리뷰어 주장은 코드와 대조해 맞을 때만 수용한다 — 확신 있게 틀린 지적을 그대로 고치는 것이 이 루프의 가장 큰 위험이다.

- 수정은 팀 위임 규칙(`memory/claude-base.md` §서브에이전트 위임)을 따른다 — 검증 루프·완료 기준을 명시하고, 커밋은 이 세션이 한다
- 검증: 서비스 카탈로그의 lint·test·build. 공유 DB를 바꾸는 DB 테스트는 일회용 컨테이너에서 돌린다 — e2e·개발 데이터를 지우지 않기 위해
- 커밋 `[{이슈}] PR 리뷰 반영: {요지}` 후 push — 기본 모드는 사용자 확인, `--auto`는 진행한다. base가 움직였으면 로컬 시험 머지로 충돌·테스트를 본 뒤 되돌린다
- 답글은 스레드 **첫 코멘트 ID**에 단다(GitHub은 답글의 답글을 받지 않는다). 한 스레드에 제안이 둘 이상이면 첫머리에 어느 제안인지 적고, 반영 커밋 SHA와 검증 결과를 넣는다. 단 답글 ID는 상태 파일에 기록한다

완료: 열린 항목마다 답글이 있고, 반영분이 push됐다.

### 5. 재리뷰 요청

같은 리뷰어 pane에 `/ad:code-review {owner/repo#N}`를 보낸다. `/ad:code-review`는 앞선 라운드를 먼저 읽어 해소 여부와 새 회귀만 판정한다. 게시 답(2단계)에는 판정 표지 규칙을 매번 다시 붙인다 — 리뷰어 세션이 바뀌면 이전 라운드의 지시를 기억하지 못한다. 그다음 2단계로 돌아간다.

### 6. 완료

- 판정 `리뷰 완료`, 열린 항목 0, `mergeable` CLEAN. base가 움직였으면 시험 머지·테스트 통과까지 본다
- 보고: 라운드 수, 반영 커밋, 반박·보류 항목, 리뷰어가 남긴 배포 후 확인 요청
- 정리: 이 세션이 만든 리뷰어 pane을 닫고 이름을 해제한다. 머지는 사용자가 한다 — 머지는 위임 범위 밖이다

## 멈춤 조건

- 라운드 상한 도달, 또는 같은 항목에서 새 논거 없이 지적·반박이 되풀이될 때 → 양쪽 입장을 사용자에게 보고하고 멈춘다. 합의를 만들려고 루프를 더 돌리면 PR만 늘어진다
- 리뷰어가 diff 밖이거나 근거 없는 지적을 반복할 때 → 보고 후 멈춘다
- 위임 범위 밖 행동(force push, base 변경, 티켓 상태)이 필요할 때 → 사용자에게 묻는다
