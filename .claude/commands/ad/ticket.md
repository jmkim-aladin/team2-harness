# YouTrack 티켓 생성

사용자 요청을 기반으로 5W1H 형식의 YouTrack 티켓을 생성한다.

> 문서 위치 결정: harness `policies/knowledge-base-policy.md` (repo↔vault 경계) + vault `wiki/guides/document-placement.md` (vault 내부 트리).

## 검증 순서

[policies/hypothesis-verification-order.md](../../../policies/hypothesis-verification-order.md) 적용 — 티켓 본문에 미확정 사실을 적기 전에 콜그래프/grep + dev DB 읽기 쿼리로 답이 나오는지 먼저 확인. 잔여 항목만 보고자/오너 컨펌 대상으로 남긴다.

## 기본값

- **프로젝트**: DEV2
- **담당자**: 대상 서비스의 owner를 `policies/team-members.md`에서 참조 (없으면 사용자에게 질문)
- **유형**: Task
- **Phase**: Backlog (ToBe)
- **우선순위**: 보통 (Normal)

티켓 작성 시 아래 문서에서 **해당 절만** 읽는다 (범위는 `ticket-guide.md` 상단 인덱스로 확인 — 실행 지침 1단계와 같은 규칙).

| 문서 | 경로 | 참조 항목 |

| **티켓 작성 가이드** | `docs/sprint/ticket-guide.md` | 5W1H 상세 작성법, 스프린트 상태, 티켓 크기 |
| **스토리 포인트 가이드** | `docs/sprint/story-point-guide.md` | SP 산정 기준, 등록 Task 상한 3 |

### 핵심 규칙 요약

- **Feature 총 기간 ≤ 1주 (필수)** — 초과 시 분할. 시작일~종료일이 7일을 넘으면 기본: 생성 차단. 단, 사용자가 1주 초과를 명시 결정하면 경고 출력 후 진행 (아래 "Feature 1주 룰 예외")
- **Task ≤ 1일 (필수)** — 초과 시 분할
- **단계 분리 판정 (필수)** — 개발 / 검증(테스트·QA) / 배포·운영 반영. **Feature와 Task 양쪽에 적용.** 단계가 여럿이면 단계 수만큼 Feature를 만든다 (아래 "단계 분리" 절)
- **환경 분리 (필수)** — 개발·스테이징·운영을 한 티켓에 담지 않는다. 검증은 개발 환경 반영이 선행 조건 (아래 "환경 분리" 절)
- **제목 품질 (필수)** — `docs/sprint/ticket-guide.md` §3 제목 작성 원칙에 따라 완료 결과·업무 능력을 제목에 두고 구현 기술은 본문으로 내린다. 기술 자체가 변경 목표일 때만 기술명·버전을 제목에 둔다
- **직급 기반 gate 금지** — `선임 리뷰`·`리더 승인`만을 별도 Task나 완료 조건으로 만들지 않는다. 필요한 외부 승인은 확인 대상·책임 역할·증적으로 적는다
- **예상 시작 일자 필수**
- **전월 마지막 주에 계획 완료**

## 실행 지침

사용자가 `/ad:ticket` 또는 `/ad:ticket [설명]`을 입력하면:

0. **토큰 owner 검증 (필수)**: 위 §토큰 owner 규칙을 따른다 — owner가 본인이 아니면 **티켓 생성을 중단**한다.
1. **`docs/sprint/ticket-guide.md`에서 필요 절만 읽는다** — 기본: §2(크기·단계·환경 분리)·§3·§3-0(5W1H·Task)·§3-2·§3-3(용어·서술). 상단 인덱스로 범위 확인, 통째로 읽지 않는다
2. 사용자 입력이 있으면 해당 내용을 기반으로 티켓 작성
3. 사용자 입력이 없으면 어떤 티켓을 만들지 질문. **질문 규율**: 한 번에 하나씩만 묻고, 각 질문에 추천안을 함께 제시한다. 파일·티켓·카탈로그에서 조회 가능한 **사실**은 직접 찾고 사용자에게는 **결정**만 묻는다. 5W1H 합의 전에 생성하지 않는다
4. **대상 서비스가 명확하면** 서비스 카탈로그(`catalog/*.yaml`)를 읽어 컨텍스트 보강
5. **관련 KB 문서가 있을 수 있으면** YouTrack KB API로 검색하여 참조 (선택적)
6. **담당자 설정 (필수)**: `policies/team-members.md`에서 대상 서비스의 owner를 조회하고, 티켓 생성 후 **반드시** YouTrack REST API(`POST /api/issues/{idReadable}`)로 `Assignee` 커스텀 필드를 갱신한다. owner를 확인할 수 없으면 `jmkim` (김정민)을 기본 담당자로 설정한다. 담당자 미설정 티켓은 허용하지 않는다.
7. **SP 산정**: `docs/sprint/story-point-guide.md` 기준표에 따라 산정 제안
   - **Feature 유형은 SP `0` 고정** (하위 Task SP 합으로 Velocity 자연 집계, 중복 카운트 방지). Feature 생성 시 Story points 필드를 명시적으로 `0`으로 설정한다
   - **등록 Task의 SP 상한은 3.** 1/2/3 중에서만 산정한다. 5 이상이 나오면 포인트를 올리지 말고 **Task를 쪼갠다** (SP 가이드 §4 등록 Task 상한 규칙). 산정표의 5/8/13 구간은 분할 전 크기 감각용이다
8. **Feature 기간 검증 (필수)**: 유형이 Feature일 때 아래 검증 수행
   - 예상 시작일 ~ 종료일(또는 하위 Task 완료 예상일)이 7일 초과면 기본: **생성 차단**. 단, 사용자가 1주 초과를 명시 결정하면 경고 출력 후 진행 (아래 "Feature 1주 룰 예외")
   - 사용자에게 분할 방안을 제안하고, 분할 후 재작성
   - 분할 기준 우선순위: **① 단계별(설계 → 개발 → 개발 환경 반영 → 검증 → 운영 환경 반영) → ② 환경별 → ③ 도메인·의존성별**
9. **단계·환경 분리 판정 (필수)**: 아래 "단계 분리" / "환경 분리" 절의 절차를 수행한다. 초안을 사용자에게 제시할 때 판정 결과를 함께 출력한다
10. **제목·리뷰 조건 검사 (필수)**: `docs/sprint/ticket-guide.md` §3 제목 작성 원칙과 §3-0 리뷰 조건 작성 원칙으로 Feature·Task 제목과 완료 조건을 검사한다. 구현 상세가 제목에 있으면 결과 중심으로 고치고, 직급 기반 gate는 검증 가능한 결과 또는 실제 owner의 확인 증적으로 바꾼다

## 단계 분리 (필수)

규칙 SoT: `docs/sprint/ticket-guide.md` 2-2항 (실행 1단계에서 이미 읽는다). 아래는 실행 절차만.

| 계층 | 규칙 |
|------|------|
| Feature | 한 단계만 담는다. 단계가 여럿이면 **단계 수만큼 Feature를 만든다** |
| Task | 그 Feature의 단계 안에서만 분해한다. 개발 Feature 아래 검증·배포 Task 금지 |

### 표준 Feature 체인

| 순서 | 단계 | Feature 제목 | 선행 조건 |
|------|------|-------------|-----------|
| 1 | 설계·분석 | `[{서비스}] {업무 요약} — 설계` | — |
| 2 | 개발 | `[{서비스}] {업무 요약}` | 설계 종료 |
| 3 | 개발 환경 반영 | `[{서비스}] {업무 요약} — 배포·반영 (개발)` | 개발 종료 |
| 4 | 검증 | `[{서비스}] {업무 요약} — 테스트` / `— QA` | **개발 환경 반영 종료** |
| 5 | 운영 환경 반영 | `[{서비스}] {업무 요약} — 배포·반영 (운영)` | 검증 종료 |

- **3번과 4번을 한 Feature에 담지 않는다.** 개발 환경에 반영돼야 테스트·QA를 시작할 수 있다.
- 해당 없는 단계는 Feature를 만들지 않는다. 개발 Feature `How` 마지막에 `- 검증 해당 없음 — {사유}` / `- 배포·운영 반영 해당 없음 — {사유}` 를 남긴다.
- 나눈 Feature끼리 **선행·후행 링크를 건다.** 각 Feature는 SP `0`, 하위 Task만 산정.

### 판정 절차

초안 확정 전 아래 판정은 필수 항목이다.

| 단계 | 판정 질문 | 결과 처리 |
|------|-----------|-----------|
| **개발** | 코드·설정·데이터·SP 변경이 있는가 | 있으면 Feature 생성 (사실상 항상) |
| **검증** | 개발 산출물을 별도로 검증해야 하는가. 필요하면 어떤 형태인가 | 필요 → 형태별 Feature / 불필요 → 사유 기재 |
| **배포·운영 반영** | 어느 환경에 반영이 필요한가. 반영 후 확인이 필요한가 | 필요 → **환경별** Feature / 불필요 → 사유 기재 |
| (설계·분석) | 구현 전 정책 결정·영향도 분석이 선행되어야 하는가 | 필요할 때만 별도 Feature |

- **필요로 판정하면 반드시 별도 Feature로 분리한다.** 개발 Feature의 하위 Task나 본문 체크리스트, DoD 항목으로 대체하지 않는다.
- 판정 근거가 모호하면 사용자에게 **한 번에 하나씩** 묻는다.

### 검증 단계: 테스트 / QA 구분

검증은 **주체가 다른 두 종류**다. 셋 중 하나를 판정한다.

| 형태 | 수행 주체 | 생성 Feature |
|------|-----------|--------------|
| **테스트** | 개발2팀 내부 | `— 테스트` 1개 |
| **QA** | 시너지팀 (외부) | `— QA` 1개 |
| **테스트 → QA** | 내부 후 시너지팀 | `— 테스트`, `— QA` **2개로 분리** (순차 의존, 한 Feature에 묶지 않음) |

- 대부분의 업무는 **내부 테스트**로 판정된다. 테스트만으로 충분하면 QA를 만들지 않는다.
- **QA는 시너지팀 일정에 의존**한다. 의존 대상(개발 환경 반영 완료 시점)과 대기 구간을 본문 `When`/`How`에 명시한다.
- 형태가 애매하면 **테스트/QA/테스트 후 QA 중 무엇인지 묻는다.**
- 불필요 판정이 타당한 예시는 SoT 2-2항 "해당 없음 판정 예시" 표.

## 환경 분리 (필수)

규칙 SoT: `docs/sprint/ticket-guide.md` 2-3항.

| 대상 | 규칙 |
|------|------|
| Feature | 한 환경만 다룬다. 개발 환경 반영과 운영 환경 반영은 별도 Feature |
| Task | 한 환경만 다룬다. "개발·운영 서버 구성" 같은 묶음 Task 금지 |
| 제목 | 환경이 갈리면 끝에 표기 — `— 배포·반영 (개발)` / `(운영)` |

- 환경 축이 없는 작업(공통 모듈, 설계·조사·문서)은 분리 대상이 아니다.
- 검증도 환경이 갈리면 나눈다. 스테이징을 쓰는 서비스는 단계를 하나 더 둔다.

### 제목·필드

**Feature 제목** — 단계 구분자를 붙인다.
- 설계: `[{서비스}] {업무 요약} — 설계`
- 개발: `[{서비스}] {업무 요약}` (구분자 없음)
- 테스트: `[{서비스}] {업무 요약} — 테스트`
- QA: `[{서비스}] {업무 요약} — QA`
- 배포: `[{서비스}] {업무 요약} — 배포·반영 ({환경})`

**Task 제목** — `[{서비스}] {세부 작업}`. **구분자를 붙이지 않는다.** Subtask 링크가 부모 Feature를 가리키므로 단계·환경이 중복된다. 환경이 필요하면 작업 이름 자체에 담는다 (`개발 클러스터 생성 요청`).
- SP: 각 Task 독립 산정. 검증·배포 Task를 `0`으로 두지 않는다 (`0`은 Feature 전용)
- 담당자: 테스트는 개발 담당자 또는 팀 내부, **QA는 시너지팀**, 운영 환경 반영은 기획·운영 협업 구간일 수 있다. 서비스 owner를 기본값으로 넣되 다른 담당자가 필요한지 사용자에게 확인한다
- 운영 환경 반영 Task는 프로덕션 배포 사람 승인이 포함되므로 개발 Feature 완료만으로 종료 처리하지 않는다

### 용어 주의

"배포·운영 반영"은 **운영 환경 반영 작업**을 뜻한다. `docs/sprint/sprint-planning-overview.md`의 업무 유형 **"운영 업무"(반응적 CS·버그 대응)** 와 다른 개념이므로 혼용하지 않는다.

## 티켓 출력 형식

```
## 티켓 정보
- **제목**: [{서비스}] {작업 요약}
- **담당자**: {서비스 owner} ({이름})
- **유형**: Task
- **Phase**: Backlog (ToBe)
- **우선순위**: 보통 (Normal)
- **스토리 포인트**: {Task: 1|2|3 / Feature: 0 고정} (산정 근거: 복잡도/불확실성/작업량 — Feature는 하위 Task 합산이라 0)
- **예상 시작 일자**: {YYYY-MM-DD}
- **OKR 연계**: {팀 KR 번호} (해당 시, vault wiki/processes/okr/ 참조)

---

(5W1H 본문은 docs/sprint/ticket-guide.md 3항의 형식을 따름)

* ### What (무엇을 할 것인가)
* ### Why (왜 필요한가)
* ### Who (누가 사용할 것인가)
* ### When (언제 수행/발생하는가)
* ### Where (어디에 적용되는가)
* ### How (어떻게 구현할 것인가)
```

초안을 제시할 때 **단계·환경 분리 판정 결과를 먼저 출력**하고, 그 뒤에 Feature별 5W1H 본문과 하위 Task를 붙인다.

```
## 단계·환경 분리 판정

| 순서 | 단계 | 환경 | 판정 | Feature 제목 | 선행 |
|------|------|------|------|-------------|------|
| 1 | 개발 | — | 필요 | [{서비스}] {업무 요약} | — |
| 2 | 배포·반영 | 개발 | 필요 | [{서비스}] {업무 요약} — 배포·반영 (개발) | 1 |
| 3 | 검증 | 개발 | 필요 — 테스트 | [{서비스}] {업무 요약} — 테스트 | 2 |
| 4 | 배포·반영 | 운영 | 필요 | [{서비스}] {업무 요약} — 배포·반영 (운영) | 3 |

> 설계·분석 해당 없음 — {사유}
```

해당 없는 단계는 행을 만들지 않고 표 아래에 사유 한 줄을 남긴다.

검증이 `테스트 → QA`면 두 Feature로 나눠 출력한다.

```
| 3 | 검증 | 개발 | 필요 — 테스트 → QA | [{서비스}] {업무 요약} — 테스트 | 2 |
| 4 | 검증 | 개발 | 필요 — 테스트 → QA | [{서비스}] {업무 요약} — QA (시너지팀) | 3 |
```

각 Feature는 5W1H 본문 + 하위 Task 표를 이어서 출력한다. 하위 Task는 **그 Feature와 같은 단계·같은 환경**만 담는다.

```
### 하위 Task

| Task 제목 | 담당 | SP |
|-----------|------|----|
| [{서비스}] {세부 작업} | 개발2팀 | 3 |
```

## 외부(사업부) 티켓 처리 규칙 (필수)

본인이 직접 생성하지 않은 티켓 — 특히 사업부(기획자·운영팀·CS) 생성 티켓 — 은 **원본을 변경하지 않는다**.

### 식별 기준
- `reporter` 필드가 본인(현재 사용자) 외 다른 사람
- 사업부/기획자/운영팀이 작성한 요청 티켓 (예: `[만권당]` 요청 사항 형식, 본문에 "기능 추가 요청드립니다" 등)
- 본인이 작성한 티켓이라도 다른 팀에 공유된 경우는 외부 취급

### 금지 행위
- Type 변경 (Task → Feature 등)
- Assignee·CC·Service·Platform·Story points 등 필드 변경
- description / summary 수정
- State 임의 전환 (운영 정책상 허용된 전환만 가능)

### 표준 처리 절차
1. 외부 티켓 원본은 **그대로 둔다**
2. 본인이 작업할 단위로 **신규 Feature를 생성**한다
   - 제목 끝에 `(개발)` 같은 구분자 추가 권장
   - 본문 첫 줄에 "## 상위 요청 — 사업부 요청 티켓 {외부 ID} 하위 개발 Feature" 명시
3. 신규 Feature를 외부 티켓의 **Subtask로 링크** (외부 티켓 parent for, 신규 Feature subtask of)
4. 하위 Task 9개는 모두 **신규 Feature 하위**로 생성·링크 (외부 티켓 직접 자식으로 두지 않음)

### YouTrack 링크 API

Subtask 링크 추가·제거는 [youtrack/api-guide.md](../../../youtrack/api-guide.md) §Subtask 링크 생성을 따른다 (linkType id는 인스턴스 설정값이라 조회해서 쓴다).

## 본문 작성 규칙 (필수)

DEV2-5512 작업에서 사용자가 확정한 규칙. 모든 신규 티켓에 동일 적용한다.

### 제목
- Feature·Task 동일하게 `[{서비스명}] {업무 요약}` 형식 통일
- 서비스명은 한글 (`[만권당]`, `[투비]`, `[바자르]`)
- 날짜·버전·일정 표기 금지

### 본문
- **비즈니스 로직·정책·트리거·운영 영향 위주**로 작성
- **코드 레벨 디테일 최소화**: 컬럼명·SP명·파일경로·테이블명 나열 금지. 필요 시 도메인 단위(`공급사 계약 도메인`, `정산 처리 로직`)로 표현
- **코드블록 자제**: 본문에 ` ``` ` 사용 금지. 항목은 bullet/표로 표현
- **계획 시점으로 서술** (SoT 3-3항): 본문은 작업 시작 전 시점으로 쓴다. 이미 끝난 작업도 같다 — 진행 상태는 State가 표현한다
  - 사후 서술 신호 — `~했다` `~한 적이 있다` `전례가 있어` `한 번도 ~하지 않았다` `이미 ~있다` `빠뜨린` `A를 B로 바꾼다/전환한다`. 발견하면 SoT 3-3항 "고쳐 쓰기" 표대로 바꾼다
  - 편성도 같다 — "끝난 것/남은 것"으로 Feature를 가르지 않는다
- **용어는 팀에서 실제로 쓰는 말로** (SoT 3-2항): 직역·조어 금지. 직역 사례 표와 판단 기준은 SoT를 그대로 적용한다
  - 일괄 치환 후 결과를 읽는다 (근거: 조사 오치환 실사례 — `폴백와`, 과치환)
- **날짜·기간 본문에 적지 않음**: 시작일/배포일/스프린트 월 표기 금지. YouTrack 필드(`예상 시작일`, `Sprints`)에서만 관리
- **월별 스프린트 배정 표 본문 금지**: 배정은 Sprints 필드로만 관리
- 기본: **5W1H 모든 섹션 단순 bullet 1-5개**로 유지. 산문/장문 금지

### Task 본문: 수행 내용 섹션 (2026-07-15 사용자 확정, DEV2-7772 작업)
- 5W1H 관련 기존 규칙은 그대로 유지 (Feature는 5W1H 전체 섹션 필수)
- **Task**는 5W1H 전체까지는 요구하지 않음 — `### 수행 내용` 섹션에 해당 Task에서 수행하는 내용을 정리
- 정리 방식은 Task 성격에 따라 선택: 절차형 작업은 프로세스 순 번호 목록, 독립 항목형 작업은 개별 단위 bullet
- **`### 완료 기준` 섹션 필수** (2026-08-03 확정) — 그 Task를 끝났다고 판정하는 조건. 아래 "Task 완료 기준" 절
- Task가 SP 3 이상이면 `### SP 산정 근거` 섹션 추가 (SP 가이드 §4 등록 규칙)
- **"상위 Feature — DEV2-XXXX" 같은 상위 참조 블록 본문 금지** — 부모 관계는 Subtask 링크로만 표현 (본문 중복 기재 불필요)

### Task 완료 기준 (필수)

모든 Task 본문 마지막에 `### 완료 기준` 2~4개를 둔다. 작성 원칙은 SoT `docs/sprint/ticket-guide.md` 3-0항 "완료 기준 작성 원칙".

단계별 초점만 여기서 확인한다 — 검증 Task는 **"어떤 결과가 나와야 통과인가"**, 배포·반영 Task는 반영 완료 + **반영 후 확인 결과**, 설계 Task는 결정 항목과 기록 위치.

### Task 본문 표준 구성

```
### 수행 내용
- (또는 절차형이면 번호 목록)

### 완료 기준
- 확인 가능한 종료 조건 2~4개

### SP 산정 근거
- 복잡도 / 불확실성 / 작업량 중 해당 축 + 산정표 구간 (SP 3 이상만)
```

### SP 분할 선호 규칙
- 사용자 선호: **SP 3 (1 MD) 최대**로 1-2 레벨까지 분할
- SP 5/8 등장 시 → 자동으로 SP 3 단위로 추가 분할 제안
- 한 Feature 하위의 **개발 Task**는 모두 SP 3 균일이 이상적. 검증(테스트·QA)·배포·운영 반영 Task는 실제 공수대로 산정 (보통 1~2)

### 필드 기본값
- **CC**: 비움 (사용자가 명시할 때만 추가)
- **Service**: 대상 서비스 enum 반드시 설정
- **Sprints**: 사용자 명시 시에만 설정 (기본 Backlog)
- **Story points**: Feature=0, Task=3 우선

### Feature 1주 룰 예외
- 단독 진행 + 9 MD 등 1주 초과 명시 결정 시 사용자 결정 존중. 경고만 출력하고 진행
