# 시크릿 매니저 설정 요청 티켓 템플릿 (개발3팀)

> 시크릿 매니저 키 생성은 **개발3팀** 영역이다. 개발2팀 몫은 구성 설계 · 생성 요청 · 반영 후 확인이다 — [policies/team-members.md](../../policies/team-members.md) §타팀 경계.
> 요청 티켓은 **DEV3 프로젝트**에 만든다. DEV2 Feature·Task 트리로 감싸지 않는다.
> 작성 기준: [DEV3-3284](https://aladincommunication.youtrack.cloud/issue/DEV3-3284) (2026-11-11 사용자 정리본). 이전 실례: DEV3-2089.

- reporter는 토큰 owner로 박히므로 **생성 전 본인 계정인지 확인**한다 — [youtrack/api-guide.md](../../youtrack/api-guide.md) §토큰 owner 규칙.
- 최초 담당자는 본인으로 등록하고, 사용자가 검토 후 직접 전달 담당자를 지정한다. 이전 요청의 담당자나 현재 수신 팀을 근거로 자동 배정하지 않는다. 생성 시 사용자가 다른 담당자를 명시한 경우는 그 지시를 따른다 — 절차 SoT: [ticket command](../../.claude/commands/ad/ticket.md) §설정·자원 요청 티켓.
- 개발2팀 쪽 반영·확인 작업을 이 티켓에 섞지 않는다. 필요하면 DEV2에 별도로 만들고 대기 구간을 본문에 남긴다.

## 작성 규칙

- **인증 정보 평문을 티켓 본문·댓글·메신저에 남기지 않는다.** 값 전달이 필요하면 메일 등 사내 보안 전달 수단을 사용하고 티켓에는 전달 수단만 적는다. 이슈 트래커는 검색·이력이 남고 CC 범위 밖에서도 조회된다.
- 개발3팀이 직접 발급·관리하는 인증 정보는 해당 팀의 보안 절차에 맡긴다. 요청자가 전달할 값이 있을 때만 별도 전달 수단을 적는다. JSON 예시에는 키와 값의 용도를 나타내는 자리표시자를 쓴다.
- 요청서는 필요한 결과·근거·작업 대상을 중심으로 쓴다. 권한 부여·토큰 발급·콘솔 조작 등 수신 팀의 세부 절차는 위임한다. 연동에 꼭 필요한 인터페이스·제약은 요청사항·대상 정보에 적는다.
- Secret Name은 인증 정보가 아니므로 대상 정보에 적어 작업 대상을 특정할 수 있게 한다. 이름 자체를 감춰야 하는 건이면 이름도 메일로 뺀다.
- **환경을 한 티켓에 섞지 않는다.** dev와 prod를 같이 요청하면 반영 시점·승인 주체가 가려진다 — [docs/sprint/ticket-guide.md](../../docs/sprint/ticket-guide.md) §2-3.
- 항목 일부만 등록되면 나머지가 비어 인증 정보 구성이 깨지는 구조라면 대상 정보에 필요한 항목과 제약을 명시한다.
- 요청 회신까지는 **대기 구간**이다. 개발2팀 쪽 후속 작업 티켓이 있으면 그 본문 When/How에 대기 구간을 적는다.
