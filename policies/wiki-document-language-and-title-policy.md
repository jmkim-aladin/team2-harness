# 운영 위키 문서 언어와 제목 정책

## 목적

Obsidian vault(운영·도메인 지식 SSOT)와 팀 하네스 문서가 서비스별로 바로 구분되고, 한국어 사용자가 검색/검토하기 쉬운 형태로 유지되도록 문서 언어와 제목 기준을 고정한다. 저장소 경계 정의는 [knowledge-base-policy.md](./knowledge-base-policy.md) 참조.

## 적용 범위

- 팀 하네스의 `docs/`, `policies/`, `templates/`
- Obsidian vault의 `wiki/`, `registry/`, `imports/` 등 운영업무·도메인 지식 트리
- Ralph Loop, Graphify sidecar, DB 이관/CDC 진단, 레거시 현대화/DB 분리 분석 산출물
- 자동 생성 인덱스, Queue, Register, Querybook 문서

## 기본 원칙

- 파일명과 Obsidian 링크 target slug는 영어를 허용한다. 파일명은 기계 식별자이므로 한글화 대상이 아니다.
- 모든 문서 내용은 한국어로 작성한다. 여기서 내용은 frontmatter `title`, H1/H2/H3 등 섹션 제목, 본문, 목록, 표의 사람이 읽는 셀, wikilink 표시명을 포함한다.
- 코드, 식별자, API, SP, Table, CDC, DTO, Querybook, Graphify처럼 의미가 고정된 기술 용어는 영어를 허용한다.
- API/SP/Table/Column/Class/Method/File path/CSV column 같은 기술 식별자는 원문 영어를 보존한다. 단, 식별자를 설명하는 문장은 한국어로 쓴다.
- 기본: 기술 용어의 정확한 의미가 필요하면 원어를 유지하되, 처음에는 이 업무에서 하는 역할을 풀어 쓴다. 예를 들어 `Owner`는 담당 주체, `Source Gap`은 어떤 근거가 부족한지를 적는다. 문맥을 이미 아는 독자에게는 설명을 반복하지 않는다.
- 한글화의 목적은 모든 단어를 한국어로 바꾸는 것이 아니라, 문서가 한국어 독자에게 도메인 판단, 운영 기준, 이관 위험, 후속 조치를 이해할 수 있게 기술되는 것이다.
- 영어 기술 용어만으로 문서 제목을 만들지 않는다. 제목은 한국어 문장 또는 한국어 명사구가 중심이어야 한다.
- 파일명은 기존 규칙대로 `kebab-case.md`를 사용한다. `wiki/services/{service_id}/` 아래에서는 디렉터리가 서비스를 표현하므로 소유 서비스의 `service_id` 접두어를 붙이지 않는다. 서비스 디렉터리 밖 공용 위치에서 서비스 식별이 필요할 때만 접두어를 사용한다.
- H1 제목과 Obsidian `title` frontmatter는 사람이 읽는 이름이므로 서비스의 한글 표시명으로 시작한다.
- 실행 흐름·관계 필드·projection 생성 규칙은 [LLM 위키 운영 가이드](../docs/llm-wiki-operating-guide.md)를 기준으로 한다.

## 문체 — 관계가 드러나는 짧은 문장

- **한다체로 쓴다.** 하십시오체(`~ㅂ니다`) 금지. 정책·가이드·스킬 전부 동일
- 기본: 상태·수치·이름을 표시하는 표 셀은 명사형으로 쓴다. 원인·조건·행동을 설명하는 표 셀과 목록은 주어와 서술어를 살린다 — 독자가 단어 사이의 관계를 추측하지 않도록 한다.
- **군더더기를 뺀다** — `~하십시오` → `~한다`, `반드시 ~해야 한다` → `~한다`, `~하시기 바랍니다` → `~한다`
- **헤지 금지**: `기본적으로`, `가급적`, `일반적으로`. 규칙이면 단정하고, 예외가 있으면 예외를 적는다
- 근거·판단이 필요한 문장은 산문으로 쓴다. 압축의 목적은 짧게 만드는 것이 아니라 **읽는 사람이 규칙을 한 번에 파악하는 것**이다
- **예외 — 외부 커뮤니케이션**: 사업부·파트너에게 그대로 전달되는 문구(YouTrack 코멘트 예시, 파트너 안내문)는 하십시오체를 유지한다. 읽는 사람이 팀 밖이다
- 일괄 치환으로 문체를 바꿨으면 **결과를 반드시 읽는다.** 조사 오류와 과치환이 난다 (근거: 2026-08-03 일괄 치환 과치환 — "비교 가능한다"류 오타 발생. [티켓 가이드 §3-2](../docs/sprint/ticket-guide.md))

## 설명의 맥락과 상세 근거

의도: 독자가 이전 대화나 내부 식별자를 몰라도 문제, 판단 이유, 다음 행동을 자기 말로 설명할 수 있게 한다. Markdown 원본과 HTML·PDF 설명본에 같은 기준을 적용한다.

- 기본: 첫 화면에 다루는 상황과 현재 결론을 연결해서 쓴다. 이어서 왜 그 결론인지, 무엇이 달라지는지, 남은 확인이나 다음 행동을 설명한다. 짧은 설명 안에서 이어지면 별도 항목으로 나누지 않는다.
- 기본: 한 문단에는 하나의 질문에 대한 답을 담는다. 필요한 주체·조건·인과관계는 문장으로 연결하고, 단계나 카드의 개수는 설명에 맞춘다. 분량을 줄일 때는 반복과 작업 이력을 먼저 덜어낸다.
- 기본: 구체적인 상황 하나로 동작과 예외를 설명한다. 가상 사례는 예시라고 밝히며, 실제 원인이나 정책이 확인되지 않았다면 그 한계를 같은 자리에서 설명한다.
- 기본: 코드명·약어·상태값은 처음에 역할을 풀어 쓴다. 정확한 식별자는 개발 근거에 보존한다. 독자를 비개발자로 가정하기보다 이 업무의 이전 맥락을 모르는 동료로 가정한다.
- 기본: 본문은 판단에 필요한 설명을 맡고, 긴 SQL·로그·전체 설정표·과거 검토는 접을 수 있는 상세 근거나 연결 문서에 둔다. 적용 범위, 미검증 사항, 결정을 바꾸는 예외는 본문에 요약하고, 세부 확인 목록은 상세 근거에 둘 수 있다.

### HTML 등 추가 설명본

- HTML은 혼자 이해하거나 다른 사람에게 설명하기 위한 보조자료다. 사실·결정의 원본은 연결된 위키 문서나 저장소에 둔다. 이해용은 질문에 필요한 배경과 사례를, 공유용은 받는 사람이 모르는 맥락까지 설명한다.
- 기본: 스킬의 패널 수·절 수는 설명을 돕는 출발점으로 쓴다. 위키 보조자료는 이 정책의 이해 기준에 맞춰 조정하며, 사용자가 지정한 형식이나 기계가 읽는 계약 필드는 유지한다.
- 기본: 같은 주제의 기존 설명본을 갱신하고 원본 링크와 내용 기준일을 표시한다. 설명본은 원본의 사실·결정·미확인 범위를 따라가며, 편집일을 새 검증일로 표시하지 않는다.
- 기본: 그림은 본문에서 설명한 관계를 보여준다. 상자·화살표·색의 의미를 가까이에서 설명하고, 긴 순서도와 전체 계약표는 상세 근거로 옮긴다. 제목과 그림만 읽어도 연결을 이해할 수 있을 만큼 문장을 남긴다.
- 기본: 작성 후 문서만을 근거로 `어떤 상황인가 → 왜 이 판단인가 → 무엇이 달라지나 → 무엇을 확인하거나 결정하나`에 답할 수 있는지 확인한다. 빠진 연결은 보충하고, 답에 기여하지 않는 반복은 덜어낸다.

## 파일명과 제목 분리

파일명은 기계가 안정적으로 찾기 위한 이름이고, H1 제목은 사람이 탐색하기 위한 이름이다.

| 항목 | 규칙 | 예시 |
|---|---|---|
| 파일명 | 서비스 디렉터리 안은 소유 `service_id` 접두어 없는 영문 kebab-case | vault `wiki/services/storefront/analysis/bc-entity-explainer-2026-07-21.md` |
| H1/title | 한글 서비스명 + 한국어 제목 | `# 투비 SP 인벤토리` |
| 링크 표시명 | H1과 같은 한국어 이름 권장 | `[[tobe-sp-inventory|투비 SP 인벤토리]]` |

파일명과 링크 target은 영어여도 되지만, 사람이 화면에서 읽는 표시명은 한국어여야 한다.

| 허용 | 피할 표현 |
|---|---|
| `[[tobe-sp-inventory|투비 SP 인벤토리]]` | `[[tobe-sp-inventory|Tobe SP Inventory]]` |
| `- 투비 서비스 시작은 \`Tobe_ServiceStart\` SP 계약을 유지한다.` | `- StartService calls Tobe_ServiceStart.` |
| `| CDC 등급 | 판단 근거 |` | `| CDC Grade | Rationale |` |

## 생성 산출물 작성 기준

새 문서를 만들 때는 다음을 동시에 맞춘다.

- 파일명: `kebab-case.md`. `wiki/services/{service_id}/` 아래에서는 소유 `service_id` 접두어 금지 — 폴더가 이미 service_id를 담고 있어 파일명에 반복되면 링크·검색에 중복만 는다
- H1: 서비스별 한글 접두어로 시작
- frontmatter `title`: H1과 동일하거나 같은 한국어 제목
- `service` 또는 `service_id`: 기계 판별용 값 유지
- `related_services`, `related_tickets`, `related_okrs`, `related_meetings` 등 관계 필드: 가능하면 wikilink로 작성
- `relation_status`: 사람이 확인한 관계는 `confirmed`, 자동 추론은 `inferred`
- `Related Links` generated block: 기존 생성기 규칙 유지
- 서비스 노트의 `generated:related-notes` block: 자동 생성 영역으로 두고, 사람 작성 요약·판단은 block 밖에 작성

## 기존 문서 보정 기준

기존 영어 제목 문서는 대량 수동 수정하지 않는다. 아래 순서로 배치 보정한다.

1. 현재 H1/title과 파일명을 inventory로 뽑는다.
2. 서비스별 접두어 매핑으로 변경 후보를 만든다.
3. wikilink 표시명, generated block, index 영향 범위를 확인한다.
4. 파일명 변경이 필요한 경우와 H1/title만 바꿀 경우를 분리한다.
5. 팀 하네스에서 `python3 tools/generate_vault_indexes.py --vault "$LOCAL_WIKI_PATH"`와 `python3 tools/lint_vault.py --vault "$LOCAL_WIKI_PATH" --all`을 실행한다.
6. 검증 전에는 canonical 문서 제목 정비 완료로 표시하지 않는다.
