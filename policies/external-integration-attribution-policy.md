# 외부 연동 귀책 판단 정책

외부 연동·외부 시스템이 걸린 문제는 원인 분석을 시작할 때 **귀책(누가 무엇을 책임지는가)을 먼저 판단 대상으로 세운다.** 무엇이 고장 났는지만 보면 "우리 서버가 느렸다"에서 멈추고, 정산·회신·재발 방지 요청의 주체를 잘못 잡는다.

근거: 2026-11-09 DEV2-13278 — 비즈마켓 주문 중복을 처음에는 알라딘 오류로 정리했다가, 비즈마켓이 응답을 못 받은 주문을 조회·취소 없이 재주문으로 처리한 것이 중복의 직접 원인으로 드러났다. 사용자 요청 "연동이나 외부 문제의 경우에는 귀책문제를 항상 먼저 고려".

## 적용 대상

- 제휴사·외부 업체·벤더 API 연동(주문·결제·배송·정산·상품 전송 등), PG·택배·외부 인증
- 다른 회사·다른 팀이 보고한 문제로, 양쪽 시스템 상태가 어긋난 경우(건수·금액·상태 불일치)
- 사내라도 소유 팀이 다른 공통 서비스 경계를 넘는 연동 — [common-service-policy.md](./common-service-policy.md)와 함께 본다

## 판단 기준

| 항목 | 판단하는 방법 |
|---|---|
| 약속 | 연동 정의서·계약·KB에 응답 시간, 시간 초과 처리, 재전송, 취소 규정이 있는지 원문으로 확인한다. 없으면 "규정 없음"으로 적고 일반 원칙으로 판단한다 |
| 직접 책임 vs 원인 제공 | 결과(중복·누락·불일치)를 만든 행동의 주체와, 그 행동을 유발한 상황(지연·오류)의 주체를 나눠 적는다 |
| 시간 초과·응답 유실 | 응답을 못 받은 요청은 "결과 모름"이다. 조회·같은 키 재전송·취소로 결과를 확정하는 것은 호출한 쪽 몫으로 보고, 그 수단(조회·취소 API)이 실제로 제공됐는지 확인한다 |
| 멱등성 | 우리 API가 같은 요청 키에 처음 결과를 돌려주는지, 중복을 키로만 거절하는지, 동시 요청을 막는지 코드로 확인한다. 우리가 보완할 점은 귀책과 분리해 개선 후보로 남긴다 |
| 증거 | 양쪽 로그(우리 IIS·APM·DB, 상대 전송·수신 로그)의 시각을 맞춰 판정한다. 한쪽 진술만으로 귀책을 확정하지 않고, 상대 로그가 필요하면 보고자를 통해 요청한다 |

## 산출물

- 위키 티켓 노트에 `## 귀책 판단` 절: 직접 책임 / 원인 제공 / 약속(규정 유무) / 처리 주체 / 우리 쪽 보완점. 확정 전에는 `[추론]`·`[미확인]`을 붙인다
- 외부 회신·보고서에는 원인과 함께 처리 주체 입장을 한 줄로 적는다. 우리 쪽 개선은 "재발 방지"로 따로 적어, 사과·책임 인정과 섞이지 않게 한다
- 귀책 입장이 정산·비용 부담으로 이어지면 결정은 사람(담당자·팀장·보고 부서)이 한다 — 에이전트는 근거와 선택지를 정리한다

## 적용 스킬

`work-prep`(서비스 추정 단계에서 외부 연동 단서가 있으면 이 정책을 로드), `ticket`, `code-review`(연동 API 변경 시 멱등성·시간 초과 처리 확인), 장애 분석([incident-response.md](./incident-response.md)).
