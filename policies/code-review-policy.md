# 코드 리뷰 정책

## 리뷰 원칙

- 모든 PR은 최소 1명의 리뷰어 승인 필요
- 본인 코드 self-review 불가 (다른 사람이 반드시 리뷰) — 작성자는 자기 가정을 보지 못한다
- 리뷰어는 코드 품질뿐 아니라 **운영 영향**도 확인
- PR 승인은 머지 판단이며 출시 준비 완료가 아니다 — PR 안전 판단에 필요한 증거는 리뷰에서 확인하고, 배포 확인은 검증 / 배포·운영 반영 Task에서 닫는다: 배포 전 검증·필수 첨부물·사람 승인은 [release-policy.md](./release-policy.md)에 따라 배포 전에, 배포 후 smoke test는 [DoD](../templates/dod-checklist.md) «배포 후»에 따라 배포 후에

## 리뷰 체크포인트

### 기본
- [ ] 요구사항(티켓)과 일치하는가
- [ ] 변경 동작과 주요 실패 경로를 검출하는 증거가 있는가 — 테스트 개수나 구현을 되풀이하는 assertion이 아니라 이 변경이 틀렸을 때 실패하는지를 본다. 로직은 실패 경로 테스트, UI는 화면·상호작용 확인, 연동은 계약·호출 실행 근거처럼 변경 종류에 맞는 증거를 요구한다. [PR 템플릿](../templates/pr-template.md) «검증 결과»(대상·환경 / 실행·기대값 / 관찰·근거 / 확인하지 못한 범위)를 참고 틀로 읽되 양식을 강제하지 않고 같은 내용의 티켓·CI·저장소 증거 링크도 인정하며, 동작이 바뀌지 않는 문서·주석 변경에는 실행 테스트를 요구하지 않는다
- [ ] 기존 컨벤션을 따르는가

### 운영 영향
- [ ] DB/SP 변경이 있는가 → 별도 승인 (단, 프론트엔드 전용 서비스 PR은 체크 대상에서 제외)
- [ ] 외부 시스템 연동 변경이 있는가
- [ ] 레거시 경계를 넘는 변경이 있는가 → LEGACY_BOUNDARY.md 확인
- [ ] 롤백 방법이 명시되어 있는가
- [ ] (변경 동작이 기능 플래그로 제어되는 경우만) OFF에서 기존 동작 유지, ON에서 통합 경로 동작, 이 변경이 새로 만드는 부작용(DB 쓰기·외부 호출)이 플래그 뒤에 격리되는가 — 플래그 OFF는 이미 실행된 부작용을 되돌리지 않으므로 데이터·외부 부작용 복구는 롤백 방법으로 따로 본다. 플래그가 없는 PR에 도입을 요구하지 않는다

### 구조 (비차단 — 시니어 관점)
- [ ] 이 변경이 드러낸 구조 신호가 있는가 — 반복 변경(같은 hunk 모양이 최근 PR에 되풀이), 데이터가 코드로, 자라는 분기 사다리, 복제 블록, 책임 경계 밖 로직, 운영 데이터 없이는 검증 불가. 증거(`파일:심볼` + 수치)가 서는 것만 올리고 이벤트에 세지 않는다 — 구조는 누적된 것이라 이 PR 작성자의 책임이 아니다. 처리(보류 / 티켓 제안 / `[제안]` 게시)는 리뷰어 사람이 고른다. 절차: [`/ad:code-review`](../.claude/commands/ad/code-review.md) 4b단계

### 현대화 관련
- [ ] 신규 코드에서 레거시 DB/SP 직접 접근이 없는가 (백엔드/API/배치/DB 레포만 해당)
- [ ] adapter를 통해 접근하는가
- [ ] 서비스 하네스 갱신이 필요한 변경인가

## 서비스별 DB/SP 체크 적용

- 프론트엔드 전용 서비스 PR은 DB/SP 변경 여부와 SP 직접 접근 여부를 코드리뷰 체크포인트에서 제외한다.
- 백엔드/API/배치/DB 스크립트 레포 또는 프론트 PR에 DB 스크립트·SP 호출 계약 변경이 함께 포함된 경우에는 DB/SP 체크를 적용한다.

## DB/SP 변경 추가 리뷰 항목 (PR 단계 첨부물 SoT)

DB 또는 SP 변경이 포함된 PR은 아래를 반드시 포함 (배포 단계 첨부물 SoT는 [release-policy.md](./release-policy.md)): 리뷰어가 영향 범위와 계약 변화를 이 두 항목 없이 diff만으로 판정하기 어렵기 때문이다.

- 영향 테이블 목록
- 입력/출력 계약 변경 사항

> 롤백 스크립트·최소 재현 데이터셋·smoke test 시나리오는 **프로덕션 배포 시점**에 별도 운영 승인 플로우에서 확인한다. PR 단계에서는 첨부 누락만으로 차단하지 않는다. 단, diff 자체가 복구할 수 없는 데이터 손실을 만들면 첨부물과 별개로 버그·운영 문제로 지적한다.

## DB 스크립트·SP PR 리뷰 범위

DB 스크립트·SP PR(예: `aladin-mall-db-script`) 리뷰의 목적은 **비즈니스 로직 추적**이다. 판정·코멘트는 분기·계산·경계값과 그 로직이 기대는 데이터 전제(요금표·코드·이력 적재 등)에 둔다.

- 배포 산출물은 작성자 몫이다 — `CREATE`/`CREATE OR ALTER` 헤더, sqlcmd 적용 명령, 롤백 SQL·절차, PR 본문 첨부물(위 절의 영향 테이블·계약 포함). 지적하지 않고, 미리보기에 올리지 않고, 이것을 근거로 리뷰 이벤트를 내리지 않는다. 첨부물이 없으면 리뷰어가 diff에서 직접 추적한다
- 배포 산출물은 [release-policy.md](./release-policy.md)의 배포 승인 흐름이 확인한다 — 같은 항목을 두 단계에서 막지 않는다

## SP 중복 호출 판정

DB 스크립트·SP PR의 로직 판정(분기·계산·경계값)에 이 질문을 넣는다: **같은 입력으로 SP가 다시 실행되면(재시도·더블클릭·배치 재실행) 이중 지급·이중 차감·중복 적재가 생기는가.**

- 막는 장치가 있으면 그 위치를 통과 근거로 적는다 — unique 제약·처리 이력 키, 상태 조건부 `UPDATE … WHERE 상태 = '대기'` 뒤 `@@ROWCOUNT` 확인, `IF EXISTS` 대신 제약 위반(2627/2601)으로 선점. 조회 후 삽입(`IF NOT EXISTS … INSERT`)은 동시 호출에서 둘 다 통과하므로 장치로 세지 않는다
- 장치가 호출자 쪽(앱의 멱등키·배치 체크포인트)에 있다고 PR·티켓이 밝혔으면 그 근거로 통과다. 확인할 수 없으면 질의 코멘트다
- 이 판정은 로직이다 — 위 첨부물이나 배포 산출물(`CREATE` 헤더·적용 명령·롤백 절차)과 섞지 않는다
