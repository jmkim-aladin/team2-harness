# `/ad:explain --tldr` — 아키텍처 one-pager 규격

처음 보는 사람이 한 페이지로 "이게 뭐고 왜 이렇게 생겼나"를 파악하는 **아키텍처 개요**를 만든다. 코드 리뷰가 아니다 — 판정도 finding도 넣지 않는다.

> 진입점·모드 판별·공통 금지는 [explain.md](../../.claude/commands/ad/explain.md)가 SoT다. 이 문서는 `tldr` 모드에서만 읽는 섹션 규격이다. 2026-10-21 `tldr` 스킬을 `/ad:explain`의 모드로 흡수했다 — 둘 다 사용자 호출 전용 설명 문서라 진입점 하나로 충분하다.

## 산출 위치

- 인자 없음: 현재 Git 저장소. 기본 산출 위치는 대상 저장소의 **gitignore된 경로**(`artifacts/PROJECT-TLDR.md` 등) — 임시 공유가 기본 용도다
- `--keep`: 커밋 대상인 `docs/TLDR.md`에 저장한다. `--out`은 경로를 직접 지정한다
- HTML 렌더(`--html`)·퀴즈는 쓰지 않는다 — 렌더러는 `diff`·`analysis` 섹션 규격을 검증한다

## 고도(altitude) — 이 모드의 단일 규율

고도를 **아키텍처**에 고정한다. 아래로 내려가면 API 문서가 되고, 위로 올라가면 홍보 문구가 된다.

| 쓴다 | 안 쓴다 |
|---|---|
| 컨셉 구성, 계층 분리와 그 이유 | 클래스 시그니처, 생성자 인수, 호출 샘플 |
| 판별 로직 (무엇으로 갈리는지) | 조건문 구현, 상수 위치 |
| 요청 생애주기 단계 | 메서드 호출 순서, 스택 트레이스 |
| 구성 요소의 **역할** | 디렉토리 트리, 파일 목록 |
| 비목표(non-goals) | 로드맵, 진행률 |

## 절차

기본 순서다 — 대상에 맞게 조정할 수 있다. 각 단계의 완료 기준은 유지한다.

1. **근거 수집.** 설계 spec·계획 문서 → 조립 지점과 public 표면 → 설정과 기본값 → 실패 처리 경로 순으로 읽는다. 미확정 사실은 [hypothesis-verification-order.md](../../policies/hypothesis-verification-order.md) 순서로 코드·grep으로 먼저 해소하고, 남은 것만 사용자에게 묻는다.
   *완료 기준*: 각 필수 섹션에 대해 근거를 `파일:심볼`로 하나 이상 댈 수 있다. 못 대는 필수 섹션은 질문하고, 선택 섹션은 뺀다.
2. **불일치 대조.** spec 문서와 코드가 다르면 **코드가 우선**이다. 불일치는 본문에 섞지 않고 마지막 보고에서 따로 알린다.
   *완료 기준*: 문서에 쓴 사실 중 코드로 확인 못 한 것이 0건.
3. **초안.** 섹션 규격의 순서대로 채운다. 규칙 하나마다 **근거(rationale) 한 절**을 붙인다 — "왜"가 없으면 독자가 규칙을 임의로 바꾼다.
4. **가지치기.** 삭제 테스트: 한 문장을 지우고 **독자의 판단이 달라지지 않으면** 그 문장은 처음부터 없었던 것이다. 다이어그램과 겹치는 목록을 먼저 지운다.
   *완료 기준*: 섹션당 8줄 이내, 전체 1,200단어 이내(`wc -w`).
5. **저장·보고.** 산출 경로, 넣은 섹션, 뺀 선택 섹션, 2단계 불일치, 근거를 못 댄 항목을 함께 보고한다.

## 섹션 규격

| # | 섹션 | 담는 것 | 필수 | 분량 |
|---|---|---|---|---|
| 1 | 한 줄 | 정체 + 왜 존재하나. 누가 쓰고 무슨 문제를 해소하나 | 필수 | 2~3문장 |
| 2 | 설계 전제 N가지 | 형태를 강제한 전제와 **그로부터 따라오는 제약**. 2열 표(전제 / 제약) | 필수 | 표 3행 |
| 3 | 구성과 역할 | **구성 다이어그램** + 구성 요소별 역할 표 + 원칙 불릿 | 필수 | 표 5행 + 불릿 3 |
| 4 | 프로세스 | **요청 생애주기 다이어그램** + 왜 그 단계가 있는지 불릿 | 필수 | 불릿 3~4 |
| 5 | 판별 로직 | 무엇을 대상으로 고르나(결정 테이블) + 무엇을 오류로 거부하나 | 필수 | 표 1개 + 불릿 3 |
| 6 | 키·데이터 형식 | 식별자 규칙, 스키마 버전 전략 | 해당 시 | 불릿 3 |
| 7 | 장애 | 실패 시 동작 + **가장 빠른 롤백 수단** | 해당 시 | 불릿 3 |
| 8 | 지표 확인 | 무엇을 보고 성공/실패를 판정하나. 대시보드가 있으면 계층별 표 | 해당 시 | 표 3행 + 불릿 2 |
| 9 | 비목표(non-goals) | 의도적으로 안 하는 것 | 필수 | 한 문단 |

2번과 9번이 이 문서의 최대 효용이다. 전제는 "왜 이렇게 이상하게 생겼나"에, 비목표는 "이걸로 뭘 기대하면 안 되나"에 답한다. 둘 다 코드를 읽어서는 알 수 없다.

프로세스(4번)는 판별 로직(5번)보다 **앞**에 둔다. 흐름을 본 뒤에야 분기 기준이 읽힌다.

## 다이어그램

mermaid 2개, [mermaid-convention.md](../../policies/mermaid-convention.md)를 따른다.

| 용도 | 유형 | 담는 것 |
|---|---|---|
| 구성 | `graph TB` | 계층 분리. 순수 계산 / 실행 경계 / 외부 I/O를 subgraph로, 주입 대상은 점선으로 |
| 프로세스 | `flowchart TD` | 요청 생애주기 + **실행 중 갈리는 분기 전부**를 판정 노드로 |

프로세스 다이어그램이 판정을 다 갈랐으면 판별 로직 섹션에는 "섞지 않는다" 같은 **규칙**만 남긴다 — 한 사실의 정답 위치는 한 곳뿐이다.

## 문체와 제외

- 평서형 단정(`~한다`). 확인 못 한 것은 쓰지 않는다
- 표와 다이어그램 우선, 불릿은 섹션당 2~4개. 산문 단락은 근거를 설명할 때만
- 상단 인용에 정본 문서 경로를 남긴다 — 이 문서는 요약이고, 요약은 낡는다
- 넣지 않는 것과 이유: 코드 예시(고도 위반) / 디렉토리 트리·파일 목록(경로 대신 역할로) / 진행 상태·커밋 수·로드맵(가장 빨리 낡아 신뢰를 깎는다) / 검증 명령·CI 게이트 목록(개요의 목적이 아니다). 진행 상태와 검증 명령은 명시 요청이 있으면 넣는다
