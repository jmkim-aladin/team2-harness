# 구조 재점검 — 시니어 관점

[`/ad:code-review`](../../.claude/commands/ad/code-review.md) 4b단계에서 구조 신호가 하나라도 보일 때 읽는다. diff 판정(기준·스펙·운영 축)은 "이 줄이 맞는가"를 묻고, 구조 재점검은 "이 변경이 어떤 구조를 드러냈는가"를 묻는다 — 반복되는 수정, 코드에 박힌 데이터, 자라는 분기 사다리는 hunk 하나하나는 전부 통과하면서도 팀 비용을 매주 가져간다.

§리뷰 범위 규칙과의 관계: 범위 규칙은 **판정**(코멘트·이벤트)을 보호한다. 구조 재점검은 판정이 아니라 **제안·티켓으로 옮기는 통로**다 — 이벤트와 승인 조건에 세지 않고, 게시는 사용자가 고른 항목만 한다. 근거: 2026-10-19 aladin-mall-db-script PR #9 — DHL 요금 OID 사다리 주간 수정이 3회째(PR #4·#7·#9)인데 hunk 판정은 매번 통과였고, 구조 제안을 둘 자리가 없었다.

## 신호 6개

| 신호 | 확인 | 증거(필수) | 방향 예 |
|---|---|---|---|
| 반복 변경 | 같은 파일·같은 hunk 모양이 최근 머지 PR에서 되풀이되는가. `gh api repos/{owner}/{repo}/commits?path={파일}&per_page=10` → 커밋 제목·PR 번호 | PR 번호 2개 이상 | 값을 데이터·설정으로 옮기고 수정을 INSERT 1건으로 |
| 데이터가 코드로 | 업무 주기로 바뀌는 값(요금·일정·기준 ID·임계값)이 리터럴로 박혀 있고 diff가 그 리터럴을 바꾸는가 | 리터럴 위치 + 변경 주기 | 유효기간(또는 기준 키) 테이블 + 단일 조회 |
| 분기 사다리 성장 | diff가 if/else·CASE 사슬에 가지를 추가하는가 | 가지 수 전 → 후 | 룩업 테이블, 범위 조회 |
| 복제 블록 | diff가 거의 같은 블록 N개 중 하나(또는 전부)를 같은 식으로 고치는가 | 복사본 수·위치 | 공통화(CASE·함수·매개변수) |
| 책임 경계 | 변경이 넣은 로직이 그 층의 책임 밖인가 — SP 안 비즈니스 규칙, 컨트롤러 안 SQL, 프론트 안 금액 계산. 기준은 서비스 카탈로그의 현대화 트랙 | `파일:심볼` + 트랙(Observe/Wrap/Extract) | 경계 뒤 adapter·서비스로 |
| 검증 불가 | 변경 결과를 운영 데이터 없이는 확인할 수 없는 구조인가(테스트 seam·픽스처 없음) | 테스트 부재 + 재현에 필요한 운영 조건 | seam·픽스처·dev 데이터 |

## 증거 기준

- 항목마다 `파일:심볼`과 **수치**(반복 N회·가지 N개·복사본 N개)를 적는다. 수치가 없으면 올리지 않는다 — 인상 비평은 작성자 시간만 쓴다
- `왜 지금` 한 줄: 이 PR이 그 신호를 어떻게 드러냈는지. 구조는 누적된 것이라 **이 PR 작성자의 책임이 아니라는 전제**로 쓴다
- 기본: 상한 3개, 반복 비용이 큰 것부터. 신호가 겹치면(반복 변경 + 데이터가 코드로) 한 항목으로 묶는다
- 넓은 조사는 하지 않는다 — 증거는 diff 파일의 변경 이력(`commits?path=`)과 그 파일 안에서 끝낸다. 레포 전체 아키텍처는 `/ad:architecture-analysis`의 몫이다

## 처리 — 사용자가 미리보기에서 고른다

| 처리 | 언제 | 모양 |
|---|---|---|
| 보류 (기본) | 신호 1회, 근거가 약함 | 미리보기에만 남는다 |
| 티켓 제안 | 반복 2회 이상이거나 운영 비용이 분명 | `/ad:ticket` 입력용 초안 한 단락 — What·Why·영향 범위. 결정 기록은 티켓이 맡는다 |
| PR `[제안]` 게시 | 작성자가 다음 라운드에서 바로 쓸 방향이고 사용자가 채택 | 리뷰 전체 메시지 끝에 `[제안]` 한 항목 — 인라인이 아니고, "머지 판단과 무관"을 명시한다 |

게시 문체는 [preview.md](./preview.md) §문체를 따르고, 주어는 "이 PR"이 아니라 "이 변경이 드러낸 구조"다 — `이 SP는 매주 OID 경계를 코드로 받습니다. 요금 유효기간 테이블로 옮기면 주간 작업이 INSERT 1건이 됩니다` 처럼 쓴다.

## 미리보기 블록

```markdown
### 구조 재점검 ({N}개) — 이벤트·승인 조건 무관
1. {신호} `{파일}:{심볼}` — {관찰} · 왜 지금: {이 PR의 증거·수치} · 방향: {한 줄} · 처리: 보류 | 티켓 제안 | [제안] 게시
```

예 (PR #9): `반복 변경 + 데이터가 코드로` `Money_DeliveryPay_Compute_5Mlg3.sql:431,480` — DHL 요금 기준 OID와 IntDate 사다리가 SP 리터럴 · 왜 지금: 같은 hunk 모양 3회째(PR #4·#7·#9), 사다리 36가지, Zone 분기 10개 복사본 ×2 · 방향: 요금 유효기간 테이블(기준 OID·IntDate) + 범위 조회 한 번 — 주간 작업이 SP 배포에서 INSERT 1건으로 · 처리: 티켓 제안
