# 코드 리뷰 미리보기 규격

[`/ad:code-review`](../../.claude/commands/ad/code-review.md) 3단계에서 읽는다. 이해 브리핑·리뷰 결과·게시 코멘트의 모양을 정한다. 판정·이벤트 규칙은 본문 §이벤트와 승인 조건이 SoT다.

## 이해 브리핑

| 항목 | 담는 것 | 기본 상한 |
|---|---|---|
| 한 줄 | 이 PR이 무엇을 왜 바꾸나. 근거는 티켓·PR 본문 | 2~3문장 |
| 검토 집중점 | 영향 범위·격리 여부·복구 가능성 → 4단계에서 깊게 볼 경로. 공통 인프라·공유 상태·외부 계약은 깊게, 격리 증거가 있는 leaf는 그 근거만큼. 판정 범위는 diff 그대로, 전체 위험표는 만들지 않는다 | 1줄 |
| 배경 2층 | `이 도메인을 처음 본다면` → `이 변경에 한정하면`. 독자는 리뷰어 | 층당 4줄 + 도식 |
| 직관 | 핵심 **하나** + 토이 데이터 예시. 코드 인용 없이 성립해야 한다 | 8줄 + 도식 |
| 변경점 묶음 | 이해 순서로 번호 붙인 세로형 목록 (아래 «핵심 코드 변경») | 핵심 3개 안팎, 코드 각 10~20줄 |
| 확인 못 한 것 | 검증 순서로 먼저 해소하고 남은 의문 | 불릿 3~5 |

상한은 기본값이다 — 중요한 변경 수와 조건문·반환·예외 경로 이해에 필요한 문맥에 맞춰 조정한다.

### 핵심 코드 변경

리뷰어가 설명 옆에서 실제 변경을 확인하고 필요한 함수·호출부까지 이어 읽게 한다.

- **선정**: 주요 동작 변화와 데이터·권한·외부 호출에 영향을 주는 변경. 정상 구현도 포함한다. 항목이 많으면 전체 묶음의 번호·제목·위치 목록을 먼저 두고 핵심 상세를 잇는다
- **배치**: `번호·제목 → 파일:줄·심볼·원본 링크 → diff → 설명`을 한 열에 쌓는다. 변경 전·후 링크는 리뷰한 리비전(`baseRefOid`/`headRefOid`)과 줄에 고정하고, 신규·삭제 파일은 존재하는 쪽만 건다
- **코드**: 수집한 diff의 문맥 줄과 `+`/`-`를 그대로 `diff` 코드블록에 발췌한다. 발췌 범위·생략 위치는 코드블록 밖에 적는다. hunk가 없는 변경은 변경 종류·경로·확인 가능한 근거를 적는다
- **설명**: 코드 바로 아래 `동작:`(전후 차이) · `볼 지점:`(직접 확인할 조건·경로) · `근거:`(관련 코드·제약·테스트 위치와 정적 확인/실행 확인/미확인) 각 1줄. 볼 지점은 확인 대상이고 결함 판정은 4단계다
- **후속 탐색**: 사용자가 "① 전체 함수 보여줘"·"② 호출부까지"라고 하면 같은 번호와 리뷰 리비전으로 함수·호출부·관련 테스트를 펼친다

### 도식

산문 4줄로 안 서는 구조 관계에만 텍스트 도식 하나를 쓴다 — 값 하나 바뀐 변경에 그리면 읽을 것만 늘어난다.

- 넣는 때: 홉 둘 이상인 호출·데이터 경로, 경계 이동(before/after), 상태·분기 전이. 셋 다 아니면 넣지 않는다
- ASCII로 쓴다 — 터미널 미리보기라 mermaid가 그려지지 않는다. `/ad:explain`의 ASCII 금지는 HTML 렌더 전제라 여기엔 적용되지 않는다
- 배경·직관 각 최대 1개, 도식당 12줄. 도식 줄은 층 상한에 세지 않는다
- 골격은 한 미리보기에 하나만: 흐름 `A → B → C` 한 줄 / 경계 이동 before·after 2단 / 분기는 들여쓴 트리
- 도식이 가른 분기를 변경점 설명으로 다시 쓰지 않는다 — 한 사실의 자리는 한 곳이다. 코드 발췌는 근거로 함께 둔다

```
before:  Controller → usp_GetOrder(SP) → DB
after:   Controller → OrderAdapter → OrderRepository → DB
                                     └ SP 경유 없음
```

## 미리보기 템플릿

미리보기는 **메시지 본문 마크다운으로 그대로** 출력한다. 아래 4-백틱 울타리는 이 문서의 템플릿 경계이고 출력물이 아니다 — 첫 줄은 `## PR #{번호} 이해 브리핑`, 코드블록은 변경점 `diff` 발췌에만 쓴다. 근거: 2026-09-17 PR #21·#747 두 세션이 울타리째 복사해 제목·링크·diff 블록이 렌더되지 않았다.

````markdown
## PR #{번호} 이해 브리핑
한 줄: {무엇을 왜 바꾸나}
검토 집중점: {영향 범위 / 격리 여부 / 복구 가능성} → {깊게 볼 경로}

### 배경
이 도메인을 처음 본다면: {4줄 이내}
이 변경에 한정하면: {4줄 이내}
{구조 관계면 ASCII 도식 1개 — 아니면 생략}

### 직관
{핵심 하나 + 토이 데이터 예시, 8줄 이내}

### 변경점 (이해 순서)
{항목이 많으면 먼저 전체 묶음의 번호·제목·위치 목록}

**① {변경 제목 — 무엇이 달라지나}**

`{파일}:{줄}` · `{심볼}` · [변경 전]({리비전·줄 고정 URL}) · [변경 후]({리비전·줄 고정 URL})

```diff
{리뷰한 실제 diff 발췌 — 문맥 줄과 +/- 유지}
```

- **동작:** {변경 전후의 동작 차이}
- **볼 지점:** {직접 확인할 조건·경로}
- **근거:** {관련 코드·제약·테스트 위치} · {정적 확인/실행 확인/미확인}

{핵심 항목별로 반복}

### 확인 못 한 것
- {의문} → 질의 코멘트 후보 / 근거 미확보

## PR #{번호} 리뷰 결과
머지: {headRefName} → {baseRefName}
작성자: {author.name}({author.login})
앞선 라운드: {N}건 — 답변됨 {N} / 미답변 {N} (없으면 `첫 리뷰`)
{릴리스 묶음 모드면 release-bundle.md의 묶음 줄·묶음 검토 블록 / 직배포 레포면 배포 경로 줄}

### 하네스 체크리스트 (통과도 근거를 댄다)
✅ 기본: 티켓 요구 3건 모두 구현 — {파일:심볼} / 테스트 {테스트명}
⚠️ 운영: DB/SP 변경 있음 — 입출력 계약 변경 미기재
❌ 현대화: 신규 코드에서 SP 직접 호출 — {파일:줄}
❓ 미확인 스펙: 연결 티켓 DEV2-1234 조회 실패 — 스펙 축 판정 불가 (티켓 자체가 없으면 `➖ 생략 스펙: 연결 스펙 없음`)
➖ 해당없음 DB/SP: 프론트 전용 PR

### 코드 코멘트 ({N}개) — [중요] → [제안] → [질문] 순
1. [중요] {파일}:{줄} — {결론} · 왜: {실제 깨지는 경로} · [축: 기준|스펙|운영] [신뢰도/심각도] [suggestion 포함]

### 교차 모델 검증: {codex|claude} {실행(문맥 모드/diff-only) 정상 완료 | 실패 — 사유 | 생략 — 사유}
양쪽 일치 {N}건 · 호스트만 {N}건 · 교차 모델만 {N}건 · 교차 [P1] {N}개 · 소요 {N}초

#### 교차 모델만 발견 ({N}개) — 채택 결정 필요
- {파일}:{줄} — {지적} [P1|P2] → 채택할까요?

### PR 밖 관찰 ({N}개) — 게시하지 않음
- {파일}:{줄} — {diff 밖에서 눈에 띈 것}

### 이벤트: {APPROVE / REQUEST_CHANGES / COMMENT}
승인 조건: 미확인 축 {N}개 · 강등된 질의 항목 {N}개 · 교차검증 {완료 — 근거|미충족 — 사유} — 셋 다 통과해야 APPROVE
### 전체 메시지: "{요약}"

### 쉬운 요약 (eli5) — 로컬 전용, 게시하지 않음
한 줄: {전문용어 0개로 — 이 PR을 어떻게 하기로 했고 왜인가}
사례: {어떤 요청·회원·상태에서 무엇이 되는가 — 값 포함 2줄}
이것만 기억: {불릿 3개}

→ 이대로 게시할까요?
````

**쉬운 요약**은 항상 마지막에 붙인다 ([eli5](../../.codex/skills/eli5/SKILL.md) §출력 형식의 1·2·5 블록). 대상은 이벤트와 전체 메시지뿐이고 코멘트를 다시 나열하지 않는다. 이벤트·심각도·승인 조건은 위 값을 그대로 옮긴다 — 값이 달라지면 요약이 아니라 다른 결론이다. 비개발 이해관계자용 한 장은 사용자 요청 시 `eli5-html`로 따로 만든다.

## 게시 코멘트

### 인라인 코멘트 골격

작성자가 첫 줄에서 무게를, 마지막 줄에서 할 일을 얻게 4블록으로 쓴다. `왜` 한 줄은 판정 장치이고 게시 본문에서는 이 골격으로 풀어 쓴다.

```markdown
**[중요] {결론 한 줄 — 무엇이 어떻게 되는가}**

{재현: 어떤 요청·입력·상태에서 그 결과가 나오는지}

{기전: 코드·SP·설정이 그렇게 동작하는 구조}

수정 제안: {방향 한 줄}
```

- 제목은 증상이 아니라 결과다. 재현을 기전보다 앞에 둔다 — 작성자가 먼저 믿어야 나머지를 읽는다
- `수정 제안:` 줄을 빼지 않는다 — 없으면 작성자의 다음 행동이 정해지지 않는다
- 본문은 기본 8줄 이내(suggestion 제외). 넘으면 결함이 두 개거나 기전을 과설명한 것이다
- 실패 경로가 다르면 같은 줄이어도 쪼개고, 같은 실패로 이어지는 요소는 묶는다 (예: HTTP 메서드 미제한은 재현 난이도 요소)
- 라벨: `[중요]` 데이터·운영·보안에 실제 영향이 있고 재현 경로를 댈 수 있다 / `[제안]` 동작은 맞고 구조·가독성·일관성 개선 여지 / `[질문]` 판정 보류, 질문 하나만
- `suggestion` 블록은 기계적으로 적용 가능한 1~10줄 수정에만 쓴다 — 클릭 한 번에 검증 안 된 설계 변경이 들어간다. 방향만 있으면 `수정 제안:` 문장으로 둔다

### 문체

- 한국어 존댓말(`~합니다`·`~됩니다`·`~을 제안합니다`)로 맺는다. 평서형 반말·명령형은 쓰지 않는다
- 주어는 코드·경로다: `검증을 빼먹었다`(✕) / `이 액션에 EventId 확인 경로가 없습니다`(○)
- 게시 본문 금지 어휘: 빼먹다, 누락했다, 실수, 잘못, 반드시 ~해야, 차단 — `차단`은 내부 판정 용어다
- `수정 제안:`은 `~로 바꾸는 방법을 제안합니다`처럼 선택지로 쓴다 — 작성자가 더 나은 방법을 알 수 있다
- 확인된 사실은 `덮입니다`처럼 단정한다 — `덮일 수 있습니다`는 완화가 아니라 정확성 손실이고, 완화는 어휘와 주어로 한다. 확인 못 한 것은 `~인지 확인 부탁드립니다`로 `[질문]`에 돌리고 헤지 섞인 지적은 만들지 않는다

### 리뷰 전체 메시지

`body`는 기본 15줄 이내로 판정 한 줄 → 변경 요약 2~3줄(이해 브리핑 `한 줄`) → `[중요]` 목록(`파일:줄` + 결론) → `[질문]` 요약만 담는다. 본문 §6의 로컬 전용 항목은 넣지 않는다.
