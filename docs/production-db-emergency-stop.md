# 운영 DB 사용자 긴급 중단

상태: 현재 계정용 실행기·stop/status CLI·취소 transport·watchdog 준비, 사용자 승인으로 lego-prod / EbookCms 일반 조회 개통(2026-10-15). 접속 진단과 30초 중단 시험은 서버 세션 종료 확인(`session_closed=true`) 및 `active=null`, `phase=idle`까지 확인했다. DB 권한 검증 상태는 `read_only_verified=false`로 유지하며, 사용자가 개통한 접속 DB만 `operator_authorized_read_databases`로 별도 허용한다. SQL 전문별 사전 승인은 유지한다. 이유: 사용자가 조회를 시작하게 한 뒤 직접 멈출 수 없는 상태를 피한다. 상위 정책은 [운영 DB 접근 정책](../policies/production-db-access-policy.md)이다.

## 사용자가 받는 기능

| 조작 | 효과 |
|---|---|
| 실행 한 건 중단 | 해당 실행의 결과 반환과 서버 작업을 취소 |
| 작업 전체 중단 | 같은 작업의 활성·대기·재시도 실행 차단, 해당 승인 회수 |
| `stop`·`$ad-db-stop`·`/ad:db-stop` | 오류 없는 사용자 취소에서 모든 운영 DB·에이전트의 활성 조회 취소, 기존 준비·승인 무효화. 서버 종료 확인과 `active=null`, `phase=idle` 뒤 다음 요청 준비를 자동 허용 |
| `emergency-stop` | 활성 조회 취소와 기존 승인 무효화 후 운영 DB 전체를 지속 차단. 명시적 `resume` 전까지 새 요청 거부 |
| 상태 확인 | 차단 시각·범위·종료 확인 수·남은 세션 수·확인 실패 원인 표시 |
| 명시적 재개 | `emergency-stop` 또는 종료 미확인·오류·재시작 차단을 사용자가 상태 확인 후 해제. 이전 조회와 승인은 자동 복원하지 않음 |

현재 계정에서 일반 취소는 `python3 /Users/jm/Documents/workspace/team2/tools/db_prod_client.py stop`으로 요청한다. 추가 승인·사유 입력·에이전트 응답은 선행 조건으로 두지 않는다. 원장 잠금이나 실행기 응답을 기다리기 전에 독립 중단 파일을 영속화하고 watchdog이 소유한 sqlcmd 프로세스를 취소한다. `status`로 `active`·`phase`·서버 종료 확인을 확인한다. 오류 없는 사용자 취소에서 종료가 확인되고 `active=null`, `phase=idle`이면 일반 취소 latch가 자동 해제된다. 오류·timeout은 종료가 확인돼도 active 슬롯만 정리하고 차단을 유지하므로 `resume`이 필요하다. `emergency-stop`은 같은 취소 절차 뒤에도 지속 차단을 남기며, `resume`이 필요하다. 개통 전 사용자가 직접 시험한다.

## sqlcmd와 중단 제어의 관계

2026-10-15 사용자 요청에 따라 정상 완료에서는 별도 세션 조회를 생략한다. 전송·출력 수신 완료, 오류와 취소 없음, 프로세스 종료 코드 0을 함께 확인한 경우만 `completion_basis=normal_exit`로 기록한다. 중단·시간 초과·통신 오류에는 기존의 서버 세션 확인을 유지하며 `completion_basis=observer`로 구분한다. 이유: 정상 조회의 추가 연결 비용을 줄이면서 비정상 종료의 확인 근거를 보존한다.

현재 Mac 계정에서는 어느 작업 디렉터리에서든 Codex의 `$ad-db-stop`, Claude Code의 `/ad:db-stop`으로 전체 중단을 요청할 수 있다. 절차는 `/Users/jm/Documents/workspace/team2/.claude/commands/ad/db-stop.md` 한 곳에서 관리한다. Codex는 `/Users/jm/.codex/skills/ad-db-stop` 전역 연결을 사용하며, Claude Code는 기존 `/Users/jm/.claude/commands/ad` 전역 연결을 사용한다. 에이전트 응답을 기다릴 수 없으면 위의 `stop` 터미널 명령을 직접 실행한다. 범위는 이 Mac의 같은 계정으로 운영 실행기를 사용하는 세션이며 별도 DataGrip 연결·개발 DB는 포함하지 않는다.

개발과 운영 모두 `sqlcmd`를 실행 도구로 사용한다. 운영은 `tools/db_prod_gateway.py`가 중앙 제어 코어·키체인·`tools/db_prod_transport.py`를 연결한다. 사용자는 전문 SQL을 터미널 또는 채팅에서 명시 승인하고, 실행기는 승인 1회를 소비한 뒤에만 접속한다. 동일 Mac 계정에서 실행하므로 사람과 에이전트를 OS 권한으로 분리하지 않는다. 단순 `Ctrl+C`, 터미널 닫기, 로컬 프로세스 종료는 중단 요청 수단이며 서버 작업 종료 확인을 대신하지 않는다.

```text
일반 조회: 에이전트 → 운영 조회 실행기 → sqlcmd/DB 연결 → SQL Server
일반 취소: 사용자 → 별도 중단 제어 서비스 → 신규 실행 차단·기존 승인 무효화
                                         → 실행 worker 취소·결과 폐기
                                         → 서버 세션/요청 종료 확인 → 다음 요청 준비
긴급 차단: 사용자 → 별도 중단 제어 서비스 → 위 절차 + 지속 차단 → 명시적 resume
보조 중단: 사용자 → 별도 관리 경로 → 전용 로그인 차단 + 남은 세션 종료
```

## 중단 처리 계약

1. **입구부터 닫는다.** 중단 범위와 세대를 중앙 원장에 영속화한다. 모든 운영 DB를 공유하는 전역 실행 슬롯과 큐·재시도·모든 worker가 같은 상태를 사용한다. 실행은 등록→차단 상태 확인→DB 전송 순으로 하며 중단과 등록 사이의 경쟁을 처리한다. 중앙 상태를 확인할 수 없으면 새 SQL 전송을 거부한다.
2. **활성 실행을 취소한다.** 실행 ID에 귀속된 연결 핸들·worker·프로세스와 실제 DB 연결 식별자를 추적한다. 전송 직전과 결과 반환 직전에도 중단 세대를 확인한다. 중단된 실행의 미반환 결과는 폐기한다.
3. **서버 상태를 확인한다.** 연결 소멸·활성 요청 부재·남은 잠금/롤백 상태를 확인한다. 반환된 종료 코드 하나로 판정하지 않는다. 이유: 테스트의 ODBC sqlcmd는 timeout에 종료 코드 0을 반환하기도 했다.
4. **확인되지 않으면 차단을 유지한다.** DB 통신 실패·취소 실패·긴 롤백은 `차단 유지·종료 미확인`으로 표시한다. active 실행과 실행 identity를 원장에 보존하고, 접수 1초·종료 확인 5초를 초기 검증 목표로 삼되 시간 초과를 중단 성공으로 표시하지 않는다. 사용자와 운영자에게 남은 대상을 보여주고 별도 관리 경로로 넘긴다.
5. **유실 worker를 자동 회수하지 않는다.** `starting`·`running` active 실행은 worker가 사라졌다는 이유만으로 슬롯·승인·DB 세션을 정리하지 않는다. 독립 관찰자가 실제 세션 종료를 확인하고 worker를 fence한 뒤에만 `reconcile`을 검토한다. 이유: 멈춘 것으로 보이는 worker가 DB 전송을 재개하는 경쟁을 막는다.
6. **오류 없는 일반 취소만 자동으로 다음 요청을 허용한다.** `stop`은 활성 실행을 취소하고 대기·재시도·미사용 승인을 무효화한다. 사용자 취소가 정상 처리되고 서버 세션 종료와 `active=null`, `phase=idle`이 확인되면 일시 중단 latch를 해제해 다음 요청을 준비한다. 새 SQL은 새 검토·승인이 필요하며 중단된 조회나 기존 승인은 되살리지 않는다.
7. **오류·timeout과 긴급 차단은 명시적으로 재개한다.** `emergency-stop`, 종료 미확인·실행기 재시작 뒤의 차단은 사용자가 상태를 확인하고 `resume`할 때까지 유지한다. 오류·timeout은 서버 종료 증거가 확인돼도 active 슬롯만 정리하고 차단은 유지하므로 `resume`이 필요하다. 세대(epoch)가 바뀌면 과거 승인과 기존 큐·자동 재시도·만료된 승인은 되살리지 않는다. 이유: 원래 중단한 조회가 복구 과정에서 다시 실행되는 것을 막는다.

사용자만 승인·지속 차단 해제 의사를 결정하고 에이전트는 그 명시 응답을 전달한다. 오류 없는 사용자 `stop`의 일시 중단 해제는 실행기의 종료 관찰 조건으로 자동 처리한다. 오류·timeout은 종료가 확인돼도 active 슬롯만 정리하고 차단은 유지하므로 `resume`이 필요하다. 같은 UID의 코드·원장 접근은 격리하지 않는다. 조회 worker 정지나 원장 잠금에 대비해 독립 watchdog과 중단 파일을 둔다. 감사 저장 장애가 긴급 중단을 막지 않게 먼저 별도 비상 기록을 남기며 일반 조회는 감사 실패 시 계속 차단한다. 실행기 자체의 장애에 대비해 사용자가 접근 가능한 DB 관리 경로도 개통 전에 확인한다.

## SQL Server의 비상 경로

운영 조회에는 서비스 앱과 공유하지 않는 전용 로그인을 쓴다. DB 관리 경로는 대상 로그인 신규 접속을 차단하고 그 로그인에 귀속된 남은 연결을 종료한다. 로그인 비활성화만으로 기존 세션은 끝나지 않는다. [Microsoft ALTER LOGIN](https://learn.microsoft.com/en-us/sql/t-sql/statements/alter-login-transact-sql)

관리자가 `KILL`을 사용해야 하면 대상 연결의 실제 소유자와 연결 식별자를 다시 확인한다. 저장해 둔 SPID만으로 반복 KILL하지 않는다. 이유: 연결이 끝난 뒤 같은 번호를 다른 연결이 사용할 수 있다. 롤백 진행 확인에는 새 KILL 대신 `WITH STATUSONLY`를 사용한다. 종료·롤백은 시간이 걸릴 수 있다. [Microsoft KILL](https://learn.microsoft.com/en-us/sql/t-sql/language-elements/kill-transact-sql)

운영 자동화는 소유한 연결 핸들의 취소를 우선하고, SPID 재사용 경쟁을 처리하지 못하는 관리 스크립트를 무인 KILL 서비스로 배포하지 않는다. 이유: 조회와 무관한 서비스 연결을 종료할 수 있다. 비상 관리자 권한과 자격증명은 에이전트에 전달하지 않는다. 관리 경로는 SP 생성·변경·삭제 없이 구성한다.

## 검증 범위와 남은 구현

Docker의 `tools/tests/integration/sqlserver/emergency_stop.py`는 공개 포트 없는 일회성 SQL Server에서만 실행한다. 중단 대상은 임시 `lab_cancel` 로그인이고 관리자는 임시 `sa`로 모사한다. 실제 DB 접속이나 권한 변경은 없다.

- 성공한 접속과 실행 중 WAITFOR 세션 두 개를 먼저 관측한다.
- 로그인 비활성화 후 신규 접속이 계정 비활성화 사유로 거부되는지 확인한다.
- 비활성화만으로 기존 두 세션은 남는다는 점을 확인한 뒤 종료한다.
- 대상 세션 소멸, 다른 로그인 세션의 계속 실행과 조회 성공을 확인한다.
- 새 관리 연결에서도 차단 상태가 남고, 읽기 계정이 이를 해제할 수 없는지 확인한다.

이 검증은 DB 중단 수단의 기능 시험이다. 추가된 `coordination.py`는 중앙 코어와 실제 sqlcmd 세션을 연결해 승인 전 접속 거부·다른 에이전트/DB 동시 실행 거부·별도 프로세스의 stop CLI·오류/timeout 취소·서버 세션 소멸·종료 미확인 시 슬롯 보존·명시적 복구를 검증한다. 취소 adapter의 관리자 권한과 KILL은 격리된 Docker 전용이며 운영 adapter가 아니다.

중앙 코어와 현재 계정 실행기의 단위 테스트는 슬롯 경쟁, 승인 변경/재사용, 미승인 비밀번호 조회·접속 차단, 결과 전달 중 중단, 감사 실패와 watchdog을 검증한다. 실제 운영의 TLS 접속과 세션 종료 관찰은 접속 진단·30초 중단 시험에서 확인했으며, 읽기 전용 권한·서버 재시작·네트워크 단절은 별도 검증 대상이다. 통과 결과만으로 운영 개통이 끝났다고 판단하지 않는다. 이유: 실제 제어 경로와 장애 시 동작은 별도로 배포·검수해야 한다.
