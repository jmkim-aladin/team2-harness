# eng-review 섹션 점검표

[`/ad:eng-review`](../../.claude/commands/ad/eng-review.md) 4단계에서 Step 0 스코프 합의 후 읽는다. 절차·질문 규율·산출물은 본문이 SoT다. 출처: [NOTICE](./NOTICE.md).

## 공통

- **네 섹션을 모두 평가한다.** "전략 문서라 구현 섹션은 해당 없다"는 항상 틀렸다 — 전략은 구현 세부에서 깨진다. 발견이 0이면 "이슈 없음"이라고 적고 넘어간다
- **발견은 질문을 거쳐 계획에 들어간다.** 조사한 뒤 발견을 계획에 한 번에 쏟아 넣고 끝내는 것이 이 리뷰가 막으려는 실패다. 비자명한 발견이 하나라도 있으면 계획 반영 전에 질문을 거친다

## 발견 형식과 신뢰도

`[P1] (신뢰도 9/10) path:line — 설명`

| 점수 | 의미 | 표시 |
|---|---|---|
| 9-10 | 코드를 읽고 확인. 구체적 결함 입증 | 그대로 |
| 7-8 | 높은 확신의 패턴 일치 | 그대로 |
| 5-6 | 보통. 오탐 가능 | "확인 필요" 단서를 붙인다 |
| 3-4 | 낮음. 수상하지만 괜찮을 수 있음 | 본문에서 빼고 부록에 |
| 1-2 | 추측 | P0급 심각도일 때만 |

**인용 게이트** — 발견을 보고하기 전에 그 발견을 유발한 코드 줄을 `path:line` + 원문으로 인용한다. "필드 X가 없다"면 필드가 있어야 할 클래스 본문을, "경쟁 조건"이면 A와 B 양쪽을 인용한다. 인용하지 못하면 미검증이다 — 신뢰도를 4-5로 내려 부록으로 보낸다.

프레임워크가 만드는 심볼은 그 생성 구조를 인용한다: JPA `@Entity`·Spring Data 파생 쿼리·`@Transactional` 프록시·MyBatis 매퍼 XML·Flyway 마이그레이션·EF 마이그레이션·Dapper 매핑·SP 본문. 이름 grep 실패는 부재의 증거가 아니다.

사용자가 신뢰도 7 미만 발견을 실제 문제로 확인하면 보정 신호다 — 같은 패턴을 다음 리뷰에서 더 높게 본다.

## 1. 아키텍처

- 시스템 설계와 컴포넌트 경계, 의존 그래프와 결합도
- 데이터 플로우와 병목, 확장성과 단일 장애점
- 보안 아키텍처 — 인증·데이터 접근·API 경계
- 핵심 흐름에 ASCII 다이어그램이 필요한가 (계획 본문 또는 코드 주석)
- 새 코드 경로·연동 지점마다 현실적 운영 장애 시나리오 하나, 그리고 계획이 대비하는가
- 새 산출물(서비스·배치·패키지·컨테이너)이면 빌드·배포·갱신 경로가 계획에 있는가 — 없으면 배포 Task 누락
- 팀 경계: 공통 서비스 영향, 레거시 공유 DB·SP 경계(SP 직접 호출 금지), 신규 앱 도메인 규칙, 서비스 소유권 — 본문 2단계에서 모은 SoT로 판정

## 2. 코드 품질

- 모듈 구조와 코드 배치
- DRY 위반 — 적극 지적
- 에러 처리 패턴과 빠진 엣지 케이스 — 명시적으로 짚는다
- 기술 부채 hotspot
- 판단 기준 대비 과잉·과소 설계
- 손대는 파일의 기존 ASCII 다이어그램이 변경 후에도 맞는가 — 낡은 다이어그램은 없는 것보다 나쁘다

## 3. 테스트

목표는 계획의 모든 코드 경로에 테스트가 있는 상태다. 계획에 테스트가 빠져 있으면 계획에 추가한다 — 구현이 처음부터 테스트와 함께 가도록.

**프레임워크 확인** — `catalog/{service}.yaml`의 `build`·`verification` → 서비스 repo CLAUDE.md의 테스트 절 → 자동 감지(`build.gradle(.kts)`·`pom.xml` → JUnit/Kotest, `*.csproj` → xUnit/NUnit/MSTest, `package.json` → jest/vitest/playwright). 못 찾으면 다이어그램은 만들고 테스트 생성 제안은 생략한다.

**Step 1 코드 경로 추적** — 진입점(컨트롤러·배치 job·리스너·화면)마다 계획된 실행을 따라간다: 입력 출처 → 변환(검증·매핑·계산) → 목적지(DB 쓰기·응답·부수효과) → 단계별 실패(null·잘못된 입력·네트워크 실패·빈 컬렉션). 변경 파일마다 추가·수정 함수, 모든 분기, 에러 경로, 호출 대상의 분기를 ASCII로 그린다.

**Step 2 사용자 흐름과 상호작용 엣지** — 흐름 전 단계 / 연타·중복 제출 / 중간 이탈 / 오래 열어둔 화면·세션 만료 / 느린 응답 / 동시 작업(두 탭) / 사용자에게 보이는 에러(메시지인가 조용한 실패인가, 복구 가능한가) / 0건·1만 건·최대 길이 경계.

**Step 3 기존 테스트 대조** — 분기·흐름마다 그것을 실행하는 테스트를 찾는다. 품질: ★★★ 동작+엣지+에러 / ★★ happy path만 / ★ smoke(렌더·예외 없음).

**E2E 판정**

- `[→E2E]` 3개 이상 컴포넌트를 잇는 흐름, mock이 실제 장애를 가리는 연동(API → 큐 → 워커 → DB), 인증·결제·데이터 삭제 흐름
- `[→EVAL]` LLM 프롬프트·시스템 지시·도구 정의 변경
- 그 외는 단위 테스트 — 순수 함수, 부수효과 없는 헬퍼, 단일 함수 엣지

**회귀 규칙** — 기존 동작을 바꾸는데 기존 테스트가 그 경로를 덮지 않으면 회귀 테스트를 계획에 critical로 넣는다. 질문하지 않는다. 애매하면 넣는다. 근거: 회귀는 무언가 깨졌다는 증거라 가장 우선하는 테스트다 (원본 규칙 승계).

**Step 4 커버리지 다이어그램**

```
CODE PATHS                                        USER FLOWS
[+] order/OrderService.kt                         [+] 주문 결제
  ├── place()                                       ├── [★★★ TESTED] 정상 결제 — OrderE2ETest:15
  │   ├── [★★★ TESTED] 정상+재고부족+타임아웃       ├── [GAP] [→E2E] 결제 버튼 연타
  │   └── [GAP]         쿠폰 만료                    └── [GAP]        결제 중 이탈
  └── cancel()
      └── [★★  TESTED] 전체 취소 — :89

COVERAGE: 4/8 경로 (50%) | 코드 2/4 | 흐름 2/4
QUALITY: ★★★:2 ★★:1 ★:0 | GAPS: 4 (E2E 1)
```

전부 덮였으면 "테스트: 새 코드 경로 전부 커버 ✓" 한 줄.

**Step 5 gap을 계획에** — gap마다 테스트 요구를 적는다: 만들 테스트 파일(기존 명명 규칙), assert(입력 → 기대 동작), 단위/E2E/eval 구분, 회귀는 CRITICAL 표시와 무엇이 깨졌는지.

**검증 단계 연결** — E2E·QA가 필요한 흐름은 검증 Task(테스트 / QA 시너지팀 — [ticket-guide.md](../sprint/ticket-guide.md) 2-2항)의 입력으로 `영향 화면·경로 / 확인할 상호작용 / 엣지 / 핵심 경로` 4줄을 `Actions`에 남긴다. QA 담당이 **무엇을 어디서** 볼지만 적고 구현 세부는 뺀다.

## 4. 성능

- N+1과 DB 접근 패턴 — 레거시 공유 DB는 SP 호출 빈도·락·인덱스를 운영 부하 기준으로 본다
- 메모리 사용
- 캐싱 기회
- 느리거나 복잡도가 높은 경로
