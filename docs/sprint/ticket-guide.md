# 스프린트 티켓 작성 및 운영 가이드

> YouTrack KB: DEV2-A-818 | 상위: DEV2-A-785 (Sprints)

## 1. 스프린트 상태 (상태값 기준)

아래 3개 상태는 스프린트 운영상 필수로 이행되어야 한다. 그 외 상태는 담당자 재량에 따라 자율적으로 운영하되, 업무 종료 시점에는 반드시 "종료" 상태로 전환되어야 한다.

- **백로그(Backlog):** 이번 스프린트에 진행하지 않을 "계획 업무" 티켓 상태 (필요는 있으나 이번 달 범위에서 제외된 항목 포함)
- **오픈(Open):** 해당 월 스프린트에서 진행할 "계획 업무" 티켓 상태. **스프린트 시작 시 계획 업무는 모두 Open 상태여야 함**
- **진행(In Progress):** Feature 및 관련 Task 작업에 착수한 상태. **동시에 task가 3개 이상 진행 상태로 있지 않도록 유의**

## 2. 티켓 단위 권장 범위

Epic은 월 단위 스프린트에서는 사용하지 않는다. 업무 범위가 월을 넘기거나, 여러 Feature를 묶어 관리할 필요가 있는 경우에는 사전 논의 후 Epic 사용으로 전환할 수 있다.

- **Feature:** 총 기간 1주일 이내 (필수). 1주일을 초과하는 Feature는 분할 필수
- **Task (Feature 하위):** 1일 이내 (필수). 1일을 초과할 것으로 보이면 Task를 더 쪼개어 작성

Feature 분할은 임의로 하지 않고 **작업 단계(2-2항)와 실행 환경(2-3항)을 1차 기준**으로 삼는다. 두 기준으로 나눈 뒤에도 1주일을 넘으면 도메인·의존성 기준으로 추가 분할한다.

### 2-1. 외부(사업부) 생성 티켓 처리 (필수)

본인이 생성하지 않은 티켓 — 특히 사업부(기획자·운영팀·CS)에서 등록한 요청 티켓 — 은 **원본을 변경하지 않는다**.

사업부에 검토 결과, 선택지, 공수 전제, 결정 필요 항목을 전달할 때는 [사업부 커뮤니케이션 정책](../../policies/business-stakeholder-communication-policy.md)을 따른다. 내부 구현명, 코드 경로, 테이블명은 사업부용 댓글의 중심 표현으로 쓰지 않고, 업무 용어로 풀어쓴 뒤 기술 근거는 로컬 위키나 개발 메모에 분리한다.

**식별 기준**
- `reporter` 필드가 본인(작업 담당자)과 다름
- 사업부 요청 형식 (예: 본문에 "기능 추가 요청드립니다", "검토 부탁드립니다" 등)

**금지 행위**
- Type 변경 (Task → Feature 등)
- Assignee·CC·Service·Platform·Story points 등 필드 임의 변경
- description / summary 임의 수정
- State 임의 전환 (운영 정책상 허용된 전환만 가능)

**표준 처리 절차**
1. 외부 티켓 원본은 그대로 둔다 (담당자·CC·본문 모두 보존)
2. 본인이 직접 다룰 단위로 **신규 Feature**를 생성한다
   - 제목 끝에 `(개발)` 같은 구분자를 붙여 외부 티켓과 구분
   - 본문 상단에 상위 외부 티켓 ID 명시
3. 신규 Feature를 외부 티켓의 **Subtask로 링크**
4. 하위 Task는 모두 신규 Feature 아래에 둔다 (외부 티켓 직계 자식으로 두지 않음)

이렇게 하면 사업부 요청 원문 변경 흔적이 남지 않고, 개발팀 작업 단위(Feature + Task)는 본인 책임 영역으로 독립 관리된다.

### 2-2. 단계 분리 (필수) — Feature·Task 공통

작업 단계(개발 / 검증 / 배포·운영 반영)는 **Feature와 Task 양쪽 모두에서 분리**한다. **하나의 Feature에도, 하나의 Task에도 개발과 검증, 배포·운영 반영을 섞어 담지 않는다.**

| 계층 | 규칙 |
|------|------|
| **Feature** | 하나의 Feature는 **한 단계만** 담는다. 개발과 검증이 함께 필요하면 Feature를 나눈다 |
| **Task** | Task 분해는 **그 Feature의 단계 안에서만** 한다. 개발 Feature 아래에 검증 Task나 배포 Task를 두지 않는다 |

> 단계 이름 "배포·운영 반영"은 **환경 반영 작업 전반**(개발·스테이징·운영)을 뜻한다. 제목 접미는 `— 배포·반영 ({환경})` 로 쓰며, 환경을 빼고 `— 배포·운영 반영` 으로만 쓰면 개발 환경 작업인지 운영 환경 작업인지 구분되지 않는다. [스프린트 계획 운영 개요](./sprint-planning-overview.md)의 업무 유형 "운영 업무"(반응적 CS·버그 대응)와는 다른 개념이다.

#### 판정 대상 단계

| 단계 | 성격 | 판정 |
|------|------|------|
| **개발** | 코드·설정·데이터·SP 구현 | 사실상 항상 존재 |
| **검증** | 내부 테스트 또는 시너지팀 QA (아래 참조) | **해당 여부·형태 판정 필수** |
| **배포·운영 반영** | 환경 반영, 반영 후 결과 확인 | **해당 여부·환경 판정 필수** (2-3항) |
| (설계·분석) | 정책 결정, 영향도 분석, 인터페이스 설계 | 필요 시에만 분리 (같은 원칙 적용) |

#### 단계가 여럿이면 Feature를 나눈다

하나의 업무가 개발·검증·배포를 모두 거치면 **단계 수만큼 Feature를 만든다.** 표준 순서는 아래와 같다.

| 순서 | 단계 | Feature 제목 | 선행 조건 |
|------|------|-------------|-----------|
| 1 | 설계·분석 | `[{서비스}] {업무 요약} — 설계` | — |
| 2 | 개발 | `[{서비스}] {업무 요약}` | 설계 종료 |
| 3 | 배포·반영 (개발 환경) | `[{서비스}] {업무 요약} — 배포·반영 (개발)` | 개발 종료 |
| 4 | 검증 | `[{서비스}] {업무 요약} — 테스트` / `— QA` | **개발 환경 반영 종료** |
| 5 | 배포·반영 (운영 환경) | `[{서비스}] {업무 요약} — 배포·반영 (운영)` | 검증 종료 |

- **검증은 개발 환경 반영이 끝나야 착수할 수 있다.** 반영 없이는 테스트할 대상이 없으므로 3번과 4번을 한 Feature에 담으면 실제 착수 가능 시점이 가려진다. 특히 시너지팀 QA는 반영 완료를 전제로 일정을 잡으므로 반드시 앞 Feature로 분리한다.
- 나눈 Feature끼리는 **선행·후행 관계로 링크**한다. 순서 의존을 티켓에 남겨야 대기 구간이 보인다.
- 업무 하나가 여러 Feature로 갈라지고 **월을 넘길 것 같으면** 2항에 따라 Epic 사용을 사전 논의한다.
- 단계를 나누면 Feature 하나의 기간이 짧아지므로 **2항의 1주일 이내 제약을 지키기 쉬워진다.** 1주일을 넘긴다면 단계 분리부터 다시 확인한다.

#### 검증 단계: 테스트와 QA 구분

검증은 **주체가 다른 두 종류**이며, 업무 성격에 따라 셋 중 하나를 선택한다.

| 형태 | 수행 주체 | 성격 |
|------|-----------|------|
| **테스트** | 개발2팀 내부 | 기능 동작·케이스 검증. 대부분의 업무에 해당 |
| **QA** | 시너지팀 | 외부 검증. 타팀 일정에 의존 |
| **테스트 → QA** | 내부 후 시너지팀 | 내부 테스트로 1차 확인 후 시너지팀 QA로 최종 검증 |

- 세 형태 중 무엇인지 **판정은 필수**이다. `테스트`만으로 충분하면 QA를 만들지 않는다.
- **테스트 → QA는 Feature 2개로 분리**한다. 순차 의존이고 주체가 다르므로 한 Feature에 묶지 않는다.
- **QA는 시너지팀 일정에 의존**하므로 대기 구간이 생긴다. QA Feature를 만들 때는 의존 대상(개발 환경 반영 완료 시점)과 대기 구간을 본문(When/How)에 명시한다 — [주간 핵심 목표 운영 정책](./weekly-goal-policy.md)의 외부 의존성 선반영 원칙과 동일하다. 과거 QA 대기가 스프린트 간 이월로 누적된 사례가 있다.

#### 원칙

1. **판정은 생략할 수 없다.** 업무를 티켓으로 옮길 때 검증(테스트/QA)과 배포·운영 반영이 필요한지 매번 확인한다.
2. **필요하다고 판정되면 반드시 별도 Feature로 분리한다.** 개발 Feature의 하위 Task나 본문 체크리스트, DoD 항목으로 대체하지 않는다.
3. **해당 없으면 Feature를 만들지 않는다.** 대신 개발 Feature 본문 How 섹션에 `검증 해당 없음 — {사유}` 형태로 한 줄 남긴다. 판정했다는 근거를 남기기 위함이다.
4. **한 Feature 안의 Task는 모두 같은 단계여야 한다.** 개발 Feature 아래 Task는 전부 개발, 검증 Feature 아래 Task는 전부 검증이다.
5. 설계·분석도 같은 원칙이다. 별도 판단이 필요하면 Feature로 분리하고, 아니면 만들지 않는다.
6. **개발의 조건은 단계가 아니다.** 대상 플랫폼·런타임·빌드 환경에서 동작하는 것은 개발이 끝났다는 조건이므로 별도 Feature로 빼지 않는다. 뒤늦게 발견해도 원래 속했어야 할 Feature에 Task로 넣는다 (3-3항). 다른 환경에서 결과가 갈리는지 **확인**하는 것은 검증 단계다.

#### 해당 없음 판정 예시

| 단계 | 해당 없음으로 볼 수 있는 경우 |
|------|------------------------------|
| 검증 | 운영 반영이 없는 조사·분석·문서 작업, 검증이 개발 Task 내 단위 테스트로 종결되는 내부 리팩터 |
| 배포·운영 반영 | 배포 산출물이 없는 설계·조사 작업, 이미 반영된 기능의 데이터만 확인하는 작업 |

#### 분리하는 이유

- 개발 완료와 서비스 반영 완료가 구분되어 스프린트 완료 판정이 정확해진다.
- 검증·반영이 개발에 묻히면 실제로는 미완인 상태로 Done 처리되어 이월·장애로 이어진다.
- **검증 착수 가능 시점이 드러난다.** 개발 환경 반영이 선행 조건이므로, 같은 Feature에 묶여 있으면 언제부터 테스트가 가능한지 보이지 않는다.
- 단계별 담당자가 다를 수 있다 (QA는 시너지팀, 운영 반영은 기획·운영팀 협업 구간).
- 단계별 Feature는 기간이 짧아 1주일 제약을 지키기 쉽고, 미완 단계가 어디인지 한눈에 보인다.

#### 제목·SP·종료 처리

- **제목 구분자는 Feature에만 붙인다.** 개발은 기존 형식 `[{서비스}] {업무 요약}` 그대로이고, 설계·검증·배포 Feature는 뒤에 구분자를 붙인다.
  - `[{서비스}] {업무 요약} — 설계`
  - `[{서비스}] {업무 요약} — 테스트` (내부)
  - `[{서비스}] {업무 요약} — QA` (시너지팀)
  - `[{서비스}] {업무 요약} — 배포·반영 ({환경})` (환경 표기는 2-3항)
- **하위 Task 제목에는 구분자를 붙이지 않는다.** Subtask 링크가 이미 부모 Feature를 가리키므로 단계·환경이 중복된다. 제목만 길어지고 정보는 늘지 않는다.
  - Task 제목은 `[{서비스}] {세부 작업}` 형식이다.
  - 환경이 Task를 읽는 데 필요하면 구분자가 아니라 **작업 이름 자체**에 담는다 — `개발 클러스터 생성 요청`, `운영 대시보드 반영`.
- **SP**: 각 단계 Feature의 하위 Task는 독립적으로 SP를 산정한다. 검증·배포 Task를 SP `0`으로 두지 않는다 (SP `0`은 Feature 전용).
- **종료**: 운영 환경 반영 Task는 프로덕션 배포 사람 승인([엔지니어링 정책](../../policies/engineering-policy.md))이 포함되므로, 개발 Feature 완료만으로 종료 처리하지 않는다. Feature는 하위 Task가 모두 종료되어야 종료한다.

### 2-3. 환경 분리 (필수)

**서로 다른 실행 환경(개발·스테이징·운영)에 대한 작업을 하나의 티켓에 담지 않는다.** Feature와 Task 양쪽에 적용한다.

#### 규칙

| 대상 | 규칙 |
|------|------|
| **Feature** | 하나의 Feature는 **한 환경만** 다룬다. 개발 환경 반영과 운영 환경 반영은 별도 Feature이다 |
| **Task** | 하나의 Task는 한 환경만 다룬다. "개발·운영 서버 구성" 같은 묶음 Task를 만들지 않는다 |
| **제목** | 환경이 갈리는 티켓은 제목 끝에 환경을 표기한다 — `— 배포·반영 (개발)`, `— 배포·반영 (운영)` |

- 환경 축이 없는 작업(소스만 만드는 공통 모듈, 설계·조사·문서)은 분리 대상이 아니다.
- 검증도 환경이 갈리면 나눈다 — 개발 환경 검증과 운영 반영 후 확인은 시점·리스크·승인 주체가 다르다.
- 스테이징 등 중간 환경을 쓰는 서비스는 같은 방식으로 한 단계를 더 둔다.

#### 인프라 의존 구간

인프라 자원 생성은 **개발3팀** 영역이다 ([팀원 정보 — 타팀 경계](../../policies/team-members.md)). 개발2팀 몫은 **구성 설계 · 생성 요청 · 코드 배포 · 대시보드 설정 · 반영 후 확인**이다.

- 개발3팀 의존 항목(클러스터 생성, 시크릿 매니저 키 생성, 접근 제어 반영)은 **별도 Task로 분리**하고 대기 구간을 본문 When/How에 명시한다. 시너지팀 QA와 같은 외부 의존 원칙이다.
- 담당자는 요청·확인을 수행하는 개발2팀 본인으로 둔다. 개발3팀 작업을 개발2팀 티켓 담당자로 넣지 않는다.

#### 분리하는 이유

- **승인 주체와 절차가 다르다.** 운영 반영은 사람 승인 구간이고 개발 반영은 아니다. 한 티켓에 담으면 승인 없이 완료 처리될 수 있다.
- **완료 시점이 다르다.** 개발 환경 반영은 검증의 선행 조건이고, 운영 반영은 검증의 후행 결과다. 두 시점 사이에 검증 구간이 들어간다.
- **롤백 단위가 다르다.** 운영 반영만 되돌려야 하는 상황에서 티켓이 묶여 있으면 이력 추적이 안 된다.
- **리스크가 다르다.** 개발 환경 실패는 내부 재시도로 끝나지만 운영 환경 실패는 장애다. 같은 SP·같은 완료 판정을 쓰면 안 된다.

## 3. Feature 작성 필수 규칙: 5W1H 기반 작성 (필수)

**Feature는 반드시 5W1H 항목을 포함해 작성**한다.

### 본문 작성 원칙

YouTrack 본문은 5W1H 기준으로 "무엇을 왜 어떻게 처리할지"만 정확하고 간단하게 기술한다. 프로젝트, 상태, 담당자, 우선순위, 스프린트, 플랫폼, 서비스처럼 YouTrack 필드에 이미 저장되는 값은 본문에 `티켓 정보` 블록으로 반복 기재하지 않는다.

- 본문에는 사용자/운영 관점의 문제, 정책, 트리거, 영향, 처리 로직, 검증 기준을 적는다.
- 본문에는 `수용 기준`, `SP 산정 기록 초안`, `운영 기준/운영 메모`처럼 별도 필드, 댓글, PR, 체크리스트로 관리할 내용을 반복 기재하지 않는다.
- 로컬 파일 경로, 로컬 산출물 경로, 개인 PC의 절대경로는 티켓 본문에 쓰지 않는다. 외부에서 접근할 수 없고, 티켓을 읽는 사람에게 재현 가능한 정보가 아니기 때문이다.
- 코드베이스 구조나 파일명 나열보다 업무 로직과 동작 흐름을 우선 설명한다. 필요한 경우에도 "로그인 검증 로직", "정산 상태 분류 로직", "배포 큐 생성 로직"처럼 도메인/기능 로직 단위로 적는다.
- 구현 위치가 꼭 필요하면 서비스명, 화면/메뉴, API/배치/모듈명 수준으로 적고, 상세 로컬 경로는 PR 또는 개발 코멘트에서 처리한다.
- 한 섹션은 1-3개 bullet을 기본으로 하고, 5개를 넘기지 않는다. 더 길어지면 티켓 본문이 아니라 별도 분석 노트나 PR 설명으로 분리한다.
- **용어는 팀에서 실제로 쓰는 말로 적는다.** 직역·조어를 만들지 않는다 (3-2항).

### What (무엇을 할 것인가)

이번 작업에서 바꾸거나 만드는 대상과 범위를 명확히 적는다.
- 개발: 기능/모듈/API/배치/정책 로직 변경 범위
- 기획: 사용자 시나리오, 정책(허용/제한/예외), 화면/플로우 변경 범위
- 디자인: 적용 화면 범위, 컴포넌트 변경/추가, 상태(로딩/오류/빈화면) 정의 범위

### Why (왜 필요한가)

이 작업이 필요한 배경과 해결하려는 문제, 기대 효과를 적는다.
- 개발: 중복 제거, 안정성/성능, 확장성, 유지보수성 개선 근거
- 기획: 운영 효율, CS 감소, 전환율/완료율 개선, 정책 준수 필요성
- 디자인: 가독성/일관성, 사용자 혼란 감소, 접근성/사용성 개선 근거

### Who (누가 사용할 것인가)

'사람 이름'이 아니라 **"사용 주체/대상"**을 적는다.
- 사용자: 고객/관리자/파트너/내부 운영자 등
- 기획/디자인: 영향을 받는 이해관계자(운영팀/CS/파트너사 등)
- 개발: 호출 주체(어댑터/서비스/배치), 연관 시스템/모듈

### When (언제 수행/발생하는가)

'배포일/배치 시간'이 아니라 **"언제 이 기능이 동작하거나 이슈가 발생하는지(트리거)"**를 적는다.
- 예: 로그인 시, 주문/결제 시, 상품 등록/수정 시, 정산 시, 특정 운영 액션 시, 스케줄 실행 시

### Where (어디에 적용되는가)

**"적용 위치"**를 적는다.
- 기획/디자인: 적용 화면/메뉴/서비스 영역 (예: 마이페이지 > 구독, 어드민 > 상품관리)
- 개발: 적용 모듈/패키지/서비스

### How (어떻게 구현할 것인가)

구현 방식뿐 아니라, 정책/화면/검증 포인트까지 "핵심만" bullet로 적는다.
- 개발: 주요 설계(인터페이스 분리, 트랜잭션/동기화, 예외 처리, 로그/모니터링)
- 기획: 정책 결정(허용/제한/예외), 운영 플로우, 데이터 기준(정의/소스)
- 디자인: 화면 구성/컴포넌트, 상태 정의(로딩/오류/빈 상태), 가이드/카피 반영

## 3-0. Task 작성 필수 규칙 (필수)

Task는 5W1H 전체를 요구하지 않는다. 대신 아래 구성을 따른다.

| 섹션 | 필수 여부 | 내용 |
|------|-----------|------|
| `### 수행 내용` | 필수 | 그 Task에서 실제로 하는 일. 절차형이면 번호 목록, 독립 항목형이면 bullet |
| `### 완료 기준` | **필수** (2026-08-03 확정) | 무엇이 나오면 끝인가. 2~4개 |
| `### SP 산정 근거` | SP 3 필수 | 복잡도·불확실성·작업량 중 해당 축과 산정표 구간 ([SP 가이드](./story-point-guide.md) §4 등록 규칙) |

> **등록 Task의 SP 상한은 3이다.** 3을 넘는 크기가 나오면 포인트를 올리지 않고 Task를 쪼갠다 ([SP 가이드](./story-point-guide.md) §4 등록 Task 상한 규칙). 2항의 `Task ≤ 1일` 제약과 같은 방향이다.

### 완료 기준 작성 원칙

- **확인 가능해야 한다.** 제3자가 보고 충족 여부를 판정할 수 있어야 하고, "잘 동작한다"는 기준이 아니다.
- **산출물로 증명된다.** 커밋·PR·테스트 통과·게이트 통과·문서·지표 화면 중 하나다. [주간 핵심 목표 운영 정책](./weekly-goal-policy.md)의 산출물 원칙과 같은 축이다.
- **수행 내용을 그대로 옮기지 않는다.** 하는 일이 아니라 끝났다고 판정하는 조건이다.
- **그 Task 안에서 닫힌다.** 다음 Task나 다음 단계에서 판정할 것을 넣지 않는다.
- 단계별로 초점이 다르다 — 검증 Task는 "어떤 결과가 나와야 통과인가", 배포·반영 Task는 반영 완료와 반영 후 확인 결과, 설계 Task는 결정된 항목과 그 결정이 기록된 위치.

> 3항 본문 작성 원칙의 "수용 기준 반복 기재 금지"는 **Feature 본문**에 대한 것이다. Task 완료 기준은 그 Task의 종료 판정 근거이므로 별개다.

### 그 밖의 Task 규칙

- "상위 Feature — DEV2-XXXX" 같은 상위 참조 블록을 본문에 쓰지 않는다. 부모 관계는 Subtask 링크로만 표현한다.
- Task는 그 Feature와 **같은 단계·같은 환경**만 담는다 (2-2항 / 2-3항).

## 3-1. 로컬 위키 티켓 노트 작성 기준

Obsidian vault의 티켓 노트는 YouTrack 본문 복제본이 아니라 **작업 판단 노트**이다. 나중에 사람이 다시 볼 때 "무엇이 문제였고, 어떤 판단으로 무엇을 해결해야 하는지"가 먼저 보여야 하며, AI가 재탐색할 수 있을 만큼의 근거 링크만 남긴다.

### 첫 화면 원칙

- 첫 50줄 안에 문제, 현재 판단, 해결 방향, 다음 행동이 모두 보여야 한다.
- 비즈니스 로직 판단을 코드 경로보다 먼저 쓴다. 예: "정산 통계는 주문 시점 스냅샷이고 실제 정산은 후속 제외 상태를 반영한다."
- 코드/SP/Table은 근거 식별자다. 본문에서는 "어떤 정책/트리거/예외를 판단하게 했는지"를 설명하고, 경로는 `기술 근거`에 짧게 둔다.
- 미확정 질문은 grep/콜그래프/개발 DB 읽기 조회로 확인해도 남는 항목만 적는다.

### 티켓 노트 기본 섹션

| 섹션 | 목적 | 길이 |
|---|---|---|
| 판단 요약 | 문제, 현재 판단, 해결 방향, 다음 행동 | 4줄 |
| 요청 요약 | 보고자, 원 요청, 제약/주의 | 3-5줄 |
| 비즈니스 로직 | 트리거, 정책, 예외, 영향 범위 | 3-5줄 |
| 기술 근거 | 진입점, SP/API/Table, 근거 링크 | 3-7줄 |
| 검증 | 확인한 방법, 결과, 남은 검증 | 3-5줄 |
| 검증 SQL | 운영/개발 검증 전달용 조회 SQL | 필요 시 |
| Actions | 다음 실행 단위 | 3-5개 |

### 길어지는 근거 처리

- 운영 서버에서 사람이 직접 확인해야 하는 SQL은 `검증 SQL` 섹션에 전문을 남긴다. 단, 판단 요약과 검증 결과 뒤에 배치해 첫 화면을 밀어내지 않는다.
- SQL은 조회 전용으로 작성하고, 실행 환경(DB/서버), 기대 결과, 결과 공유 시 필요한 컬럼을 함께 적는다.
- 전수검사 목록, 콜그래프 출력, 파일 경로 대량 목록은 티켓 본문에 붙이지 않는다.
- 긴 근거가 필요하면 `wiki/processes/tickets/dev2-{번호}/` 하위에 메모 파일로 분리하거나, 확정 지식은 `promote` 마커로 서비스 분석·결정 노트로 승격한다.
- 티켓 본문에는 `목적`, `판단 결과`, `근거 위치`, `검증에 필요한 SQL`만 남긴다.
- 표는 6행 이하의 비교·결정에만 사용한다. 목록이 7개 이상이면 "상위 3개 + 링크"로 줄인다.
- 전체 티켓 노트 본문은 완료 기록과 링크를 제외하고 120줄 이내를 기본 목표로 한다.

## 3-2. 용어 사용 원칙 (2026-08-03 확정)

티켓은 작성자 혼자 보는 문서가 아니다. 몇 달 뒤 다른 사람이 읽고, 사업부가 읽고, 마감 점검이 훑는다. **작성자에게만 통하는 말은 티켓의 수명을 깎는다.**

### 판단 기준

| 물음 | 통과 못 하면 |
|------|-------------|
| 이 팀에 처음 온 개발자가 사전 없이 이해하는가 | 팀에서 쓰는 말로 바꾼다 |
| 다른 티켓·위키·코드에 같은 말이 쓰이는가 | 이미 쓰이는 쪽으로 맞춘다 |
| 영어 원문을 모르면 뜻이 안 통하는가 | 직역이다. 표준 역어나 원어로 바꾼다 |

### 번역할 것 / 원어로 둘 것

- **업계에서 원어로 통용되는 기술 용어는 원어(또는 음차)로 둔다.** 억지 번역이 오히려 검색을 막는다 — `서킷 브레이커`, `폴백`, `롤백`, `뮤테이션 테스트`, `singleton`, `adapter`, `submodule`, `schema version`.
- **표준 역어가 자리 잡은 것은 역어로 쓴다** — `적중`(cache hit), `정규화`, `축출`(eviction), `진입점`.
- **직역해서 만든 말은 쓰지 않는다.** 원문을 모르면 뜻이 안 통하고, 팀 어디에도 그 말이 없다.

### 자주 나오는 직역·조어

실제 티켓 정리에서 걸린 사례다. 같은 유형이 보이면 오른쪽으로 바꾼다.

| 쓰지 않음 | 원문 | 대신 |
|---|---|---|
| 배선 | wiring | 설정 / 초기화 구현 |
| 조립 지점 | composition root | (대상) 초기화 지점 |
| 공개 표면 | public surface | 공개 API |
| 차단기 | circuit breaker | 서킷 브레이커 |
| 우회 (fallback 뜻일 때) | fallback | 폴백 |
| 되돌림 | rollback | 롤백 |
| 소비 서비스 / 소비 kit | consumer | 사용 서비스 / 연동 kit |
| 파라미터 축 | parameter axis | 파라미터 항목 |
| 키 영역 | key space | 키 네임스페이스 |
| 골든 벡터 | golden vector | 기준 검증 데이터 |
| 합격선 | — | 성공 기준 |
| 최저 기준 | — | 실제 버전 명시 (`.NET Framework 4.8`) |

> `우회`는 **bypass 뜻일 때는 맞는 말**이다. "경계 우회"를 폴백으로 바꾸면 의미가 뒤집힌다. 같은 단어라도 문맥을 보고 판단한다.

### 한 단어를 여러 뜻으로 쓰지 않기

`판정`·`게이트`처럼 편해서 남발하기 쉬운 말이 있다. 한 문서 안에서 뜻이 갈리면 읽는 사람이 매번 문맥을 재구성해야 한다. 뜻마다 다른 말을 쓴다 — 검사 / 확인 / 결정 / 검증 스크립트.

### 일괄 치환 시 주의

용어를 뒤늦게 정리할 때 문자열 치환만 돌리면 두 가지가 깨진다. **치환 후 반드시 결과를 읽어 본다.**

- **조사 오류** — `실패 우회와` → `폴백와` (`폴백과`가 맞음)
- **과치환** — 같은 단어의 다른 뜻까지 바뀐다. 뜻이 갈리는 단어는 문장 단위 규칙을 먼저 적용하고 단어 단위 규칙을 뒤에 둔다

## 3-3. 계획 시점 서술 원칙 (2026-08-03 확정)

**티켓 본문은 작업이 시작되기 전 시점으로 쓴다.** 티켓은 "무엇을 할 것인가"의 문서이고, "무엇을 했는가"는 코멘트·커밋·산출물 링크가 담당한다.

**이미 끝난 작업을 뒤늦게 티켓으로 남길 때도 같다.** 진행 상태는 State 필드가 표현하지 본문이 표현하지 않는다. 한 프로젝트 안에 완료분과 예정분이 섞여 있어도 **모든 티켓의 서술 시점은 같아야 한다.**

### 왜

- 본문이 사후 기록이면 같은 작업을 다시 계획할 때 재사용할 수 없다.
- 읽는 사람이 "이건 이미 끝난 건가 할 건가"를 본문에서 추측하게 된다. 그 정보는 State에 있다.
- 사후 서술은 그때의 사정(누가 무엇을 빠뜨렸는지)을 본문에 남겨 티켓을 회고록으로 만든다. 회고는 코멘트에서 한다.

### 사후 서술 신호

본문에 아래 표현이 있으면 시점이 어긋난 것이다.

| 표현 | 문제 | 고쳐 쓰기 |
|------|------|-----------|
| `~했다` / `~한 적이 있다` / `전례가 있어` | 겪은 일을 근거로 든다 | 겪은 사정 대신 **일반 원리**로 — "문자열 검사가 오판했다" → "문자열만으로는 정상 코드를 오탐한다" |
| `한 번도 ~하지 않았다` / `확인해 본 적이 없다` | 현재 진척을 서술한다 | **불확실성**으로 — "실행해 본 적이 없다" → "두 런타임의 동작 차이를 미리 알 수 없다" |
| `이미 ~있다` / `빠뜨린` / `메우기` | 앞 작업의 결과를 전제한다 | **조건**으로 — "이미 있다" → "다른 단계 산출물이라 여기서 만들지 않는다" |
| `A를 B로 바꾼다` / `전환한다` | 이전 구현의 존재를 전제한다 | "B로 **만든다** / **구현한다**" |

> 완료 기준의 `~되어 있다`는 사후 서술이 아니다. 끝난 뒤의 상태를 적는 것이 완료 기준의 형식이다.

### 편성도 같은 시점으로

- **"끝난 것 / 남은 것"으로 Feature를 가르지 않는다.** 편성 기준은 단계(2-2항)와 환경(2-3항)뿐이다.
- **개발의 조건인 것을 별도 Feature로 빼지 않는다.** 대상 플랫폼·런타임·빌드 환경에서 동작하는 것은 개발이 끝났다는 조건이지 추가 산출물이 아니다. 뒤늦게 발견해도 원래 속했어야 할 Feature에 Task로 넣는다.
- 다른 환경에서 결과가 갈리는지 **확인**하는 것은 검증 단계이므로 검증 Feature에 둔다.

## 4. 팀원 표기 규칙

티켓 본문에서 팀원을 언급할 때는 **영어 이니셜(KJM, JEH 등)이 아닌 한글 이름**으로 표기한다.

| 표기 | 예시 |
|------|------|
| ✅ 올바름 | 김정민, 조은흠, 안혜련 |
| ❌ 잘못됨 | KJM, JEH, AHR |

> 이니셜은 OKR 등 팀 내부 약어로만 사용하고, YouTrack 티켓에서는 누구나 읽을 수 있도록 이름을 사용한다.

## 5. 예상 시작 일자 (필수)

모든 스프린트 대상 티켓은 작성 시 "예상 시작 일자"를 반드시 기재한다. 시작 일자는 실제 착수일이 변동될 수 있으나, 계획 수립의 기준점으로 사용한다. 작업 예측 시간과는 별개 요소다.

## 6. 스프린트 계획 수립 시점 (필수 운영 원칙)

모든 스프린트 대상 티켓은 **전월 마지막 주에 작성 및 계획을 완료**한다.
(예: 3월 스프린트 티켓은 2월 마지막 주까지 작성/정리 완료)

## 7. 운영 원칙: 점진적 강화

티켓 관리 요소(필수 항목, 규칙, 체크리스트 등)는 한 번에 완벽히 고정하지 않고, 운영하면서 점진적으로 추가/강화한다.

## 8. 이월 규칙 (운영 업무/계획 업무 공통)

스프린트 이월 시 반드시 코멘트로 사유를 남긴다. 상세 절차는 [업무 계획 변경 절차](./plan-change-process.md)를 참조한다.

## 9. Feature 중간 변경 시 월말 분리 규칙

Feature 진행 중에 하위 Task의 범위가 일부 변경(제외/축소/연기)되더라도, **이미 진행 중인 Task는 중단하지 않고 그대로 완료까지 진행**한다. 진행 중 Task를 되돌리는 비용이 더 크기 때문이다.

월말 스프린트 마감 시점에 Feature를 다음과 같이 분리한다.

- **원본 Feature 종료**: 완료된 Task들만 묶어 기존 Feature를 완료 처리. 제목/본문에 분리 시점과 완료 범위를 명시
- **잔여 Feature 신규 생성**: 변경·미완료 Task를 모아 신규 Feature로 분리하여 다음 스프린트로 이월하거나 백로그로 보냄. 본문에 원본 Feature ID를 `relates to`로 참조

이렇게 하면 Feature 1주 룰(2항)을 깨지 않고, 한 스프린트의 완료 가치만 명확히 마감에 반영할 수 있다. 주간업무 보고서에서도 완료 Feature는 "완료된 항목"으로, 잔여 Feature는 "백로그/진행중"으로 자연스럽게 정리된다.

## 10. 태그 컨벤션

모든 스프린트 대상 티켓(Feature, Task)에 아래 태그를 부여한다.

| 태그 | 형식 | 예시 | 설명 |
|------|------|------|------|
| 역할 | `role:{역할}` | `role:개발`, `role:기획`, `role:디자인` | 담당 직군 |
| 서비스 | `biz:{서비스}` | `biz:만권당`, `biz:바자르`, `biz:투비` | 대상 서비스 |
| 스프린트 | `{YYMM}-planned` | `2604-planned` | 계획 수립 시점의 스프린트 월 |

## 11. YouTrack 필수 커스텀 필드

티켓 생성 시 아래 필드를 반드시 설정한다.

| 필드 | 필수 | 설명 |
|------|------|------|
| Type | ✅ | Feature 또는 Task |
| State | ✅ | 스프린트 대상은 Open |
| Assignee | ✅ | 담당자 (서비스 owner 기본) |
| Service | ✅ | 대상 서비스 (만권당, 투비 등) |
| Sprints | ✅ | 스프린트 월 (2026.04 등) |
| Story points | Task만 | Task에만 산정. **Feature는 SP `0` 고정** (Velocity는 하위 Task SP 합으로 자연 집계 — 중복 카운트 방지) |
| Platform | 선택 | Server, Web, iOS, Android 등 |
| Priority | ✅ | 기본 Normal |

## 12. OKR → 스프린트 변환 프로세스

분기 OKR을 월간 스프린트 티켓으로 변환하는 절차다.

```
분기 OKR (개인)
├── 해당 월 KR 항목 추출
│   └── 월별 포커스 테이블 참조
├── 단계·환경 분리 판정 (2-2항 / 2-3항) — 생략 불가
│   └── 업무 하나 → 단계 수만큼 Feature
│       ├── [업무] — 설계                      해당 시에만
│       ├── [업무]                             개발
│       ├── [업무] — 배포·반영 (개발)      검증의 선행 조건
│       ├── [업무] — 테스트 / — QA             개발 환경 반영 종료 후 착수
│       └── [업무] — 배포·반영 (운영)      검증 종료 후 착수
├── Feature 작성 (5W1H 필수)
│   └── 각 1주일 이내, SP 0 고정, 선행·후행 링크
└── Task 분해 (Feature 하위)
    ├── 1일 이내, SP 산정 (0 금지)
    └── 그 Feature와 같은 단계·같은 환경만
```

### 설계·분석 업무 SP 기준

코딩이 아닌 설계·분석·문서 작업의 SP 산정 기준이다.

| SP | 사이즈 | 설계·분석 업무 기준 |
|----|--------|-------------------|
| 1 (XS) | 즉시 완료 | 미팅, 문서 정리, 모니터링 확인, 단순 배포 실행 |
| 2 (S) | 반나절~1일 | 단일 도메인 분석·설계, 설정 작업, 기능 검증, 패턴 조사, 전환/연동을 위한 영향도 분석·보조자료 작성 |
| 3 (M) | 1~2일 | 신규 아키텍처 설계, 복합 도메인 설계, 다수 이해관계자 협의 |

> 설계 업무는 코딩 대비 작업량은 적으나 불확실성·복잡도가 높을 수 있으므로, 의사결정 난이도를 반영하여 산정한다.

## 13. YouTrack 마크다운 서식 규칙

YouTrack 티켓의 description은 마크다운을 지원한다. AI 도구(Claude Code 등)로 티켓을 생성/수정할 때 아래 규칙을 준수한다.

### 줄바꿈

MCP 등 API를 통해 description을 전달할 때 **실제 개행문자**를 사용한다. `\n` 이스케이프 시퀀스를 쓰면 리터럴 `\n`이 그대로 노출되어 한 줄로 붙는다.

| 방법 | 결과 |
|------|------|
| ✅ description 파라미터에 여러 줄 텍스트 직접 작성 | 마크다운 정상 렌더링 |
| ❌ `"## What\n내용\n## Why\n내용"` | 한 줄로 표시됨 |

### 지원 문법

헤딩(`##`), 테이블, 리스트(`-`), 인용(`>`), 코드블록(`` ``` ``), 굵게(`**`), 링크 등 표준 마크다운 문법을 그대로 사용한다.

## 14. 전사 YouTrack 상태 플로우

DEV2팀 스프린트 상태(위 1항)는 전사 YouTrack 상태 플로우 위에서 운영된다. 전체 상태 머신(ToBe → Submitted → Open → In Progress → Fixed → Closed 등)은 [YouTrack 티켓 가이드](../../youtrack/ticket-guide.md)를 참조한다.

## 15. 주간 핵심 목표 연계 (2026-08~)

개인별 주간 핵심 목표(주 2개)는 [주간 핵심 목표 운영 정책](./weekly-goal-policy.md)을 따르며, 티켓 작성·결과 처리와 다음처럼 연결한다.

- **목표 ↔ 티켓 연결**: 핵심 목표로 선정한 작업은 해당 주에 실행할 Feature/Task 티켓과 연결하고, 목표 문구에 티켓 ID를 병기한다.
- **산출물 명시**: 연결 Feature의 How(또는 하위 Task)에 "무엇이 나오면 달성인가"를 객관적으로 확인 가능한 산출물(코드 커밋, PR, 문서, 배포 기록)로 명시한다. 산출물로 증명할 수 없는 목표는 수립 단계에서 다시 정의한다.
- **외부 의존성 선반영**: 운영 반영·타팀 협업·의사결정이 걸린 티켓을 핵심 목표로 삼을 때는 의존 요소와 대기 구간을 티켓(When/How)에 명시하고, 주 내 완결 가능한 범위로 분할한다. 협업이 필요했다는 사실 자체는 미달성 사유로 인정되지 않는다.
- **결과 처리**: 주간 마감 시 산출물 링크를 티켓 코멘트로 남긴다. 미달성 시 구체 원인과 재발 방지 대응을 코멘트로 기록한다. 단순 "업무 과다/시간 부족"은 사유로 인정되지 않는다.
