# 주간업무 보고 가이드

> 출처: [YouTrack KB DEV2-A-692](https://aladincommunication.youtrack.cloud/articles/DEV2-A-692/7KO86rCE7JeF66y0)

## 1. 계획 업무 작성 원칙

기본적으로는 계획된 업무 중 개발자 담당 티켓을 기준으로 작성한다.

**기록 대상**:

- Type=Feature 또는 Epic
- 개발자 담당 티켓 우선
- 대상 월 스프린트와 일치하는 티켓
  - 예: 2026년 6월 보고서는 `Sprints=2026.06` 또는 `2606-planned`
- 기획자/디자이너 Feature 하위에 개발자 담당 Task가 있으면 부모 Feature를 컨텍스트로 사용하고 개발자 Task만 본문에 표기
- 완료 항목은 대상 월 완료분 유지

**기록 제외**:

- Backlog 상태 티켓 (코멘트에 이월 결정만 있고 아직 `Open`이면 제외하지 않는다 — §4-B.5 이월 검토 표시)
- 대상 월 스프린트가 아닌 티켓
- 기획자/디자이너 담당 Feature 중 개발자 담당 하위 Task가 없는 항목
- 사업부 작성 단발 운영 Task/Bug (통계요청·점검요청·팀장승인·앱푸시 발송 리스트·개별 사용자 문의 등)
- Type=Task/Bug 단발 대응 일반

**예외 포함**:

- 이슈 규모가 크거나 팀 차원의 공유가 필요한 운영성 업무(사업부 작성 티켓이라도 Feature 성격이면 포함 가능)
- 멀티캠퍼스 IF 개발, B2B 플랫폼 구축 등 장기 운영성 Feature

**중복 제거**:

- `DEV2-*` ID 중복은 같은 레벨에서만 제거한다.
- top-level 항목끼리 같은 ID가 반복되면 하나만 남긴다.
- 하위 본문 라인끼리 같은 ID가 반복되면 하나만 남긴다.
- top-level과 하위 본문 라인의 같은 ID 반복은 계층 표현으로 허용한다. 단일 Task나 하위가 없는 Feature는 제목과 본문 라인에 같은 ID가 반복될 수 있다.

## 2. 상태별 구분 기준

### ① 백로그

> 최종 주간업무 보고 후보에서는 Backlog 상태 티켓을 제외한다. 아래 정의는 과거 양식/조회용 참고이다.

**정의**

- 현재 진행 중인 스프린트 종료 후 시작 예정인 업무
- 우선순위 변경으로 현재 스프린트에서 제외된 업무

**작성 티켓 기준**

- 티켓 유형: Epic, Feature
- 티켓 상태: Backlog
- 스프린트: 없음

**필수 작성 요소**

- 제목
- 담당자
- 5W1H 포함 티켓 링크

**세부 항목 작성**: 불필요

### ② 미진행 항목

**정의**

- 현재 진행 중인 스프린트에 포함되었으나 아직 시작하지 않은 업무
- 우선순위 조정으로 재정렬된 업무

**작성 기준**

- 티켓 유형: Epic, Feature
- 티켓 상태: Open
- 스프린트: 현재 진행 중인 스프린트
- 보고 대상 월과 스프린트가 일치해야 함 (`YYYY.MM` 또는 `YYMM-planned`)

**필수 작성 요소**

- 제목
- 담당자
- 시작 예상 일자(~)
- 5W1H 포함 티켓 링크

**세부 항목 작성**: 선택

### ③ 진행 중 항목

**정의**

- 현재 스프린트에 포함되어 실제 작업이 진행 중인 업무
- 이전 스프린트에서 이월되어 계속 진행 중인 업무

**작성 기준**

- 티켓 유형: Epic, Feature
- 티켓 상태: In Progress
- 스프린트: 현재 진행 중인 스프린트(이월된 경우 과거 스프린트 이력 포함)
- 보고 대상 월과 스프린트가 일치해야 함 (`YYYY.MM` 또는 `YYMM-planned`)

**필수 작성 요소**

- 제목
- 담당자
- (~)완료 목표 일자
- 5W1H 포함 티켓 링크

**세부 항목 작성**: 필수

### ④ 완료된 항목

**정의**

- 현재 진행 중인 스프린트에 포함되어 완료된 업무
- 이전 스프린트에서 완료되었으나, 지난 보고 이후 완료 처리된 업무

**작성 기준**

- 티켓 유형: Epic, Feature
- 티켓 상태: Fixed (또는 완료 상태)
- 스프린트: 해당 완료 시점의 스프린트 이력 유지
- 보고 대상 월과 스프린트가 일치해야 함 (`YYYY.MM` 또는 `YYMM-planned`)
- 대상 월 완료분은 유지하며 최근 7/14일 범위로 자르지 않음

**필수 작성 요소**

- 제목
- 담당자
- 완료 일자
- 5W1H 포함 티켓 링크

**세부 항목 작성**: 선택

## 3. 세부(Task) 항목 관리 기준

Epic/Feature 하위 Task는 진행 상태를 명확히 구분하기 위해 말머리를 추가한다.

**말머리 구분**

- (완료)
- (진행 중)
- (예정)

**작성 기준**

- 티켓 유형: Task
- 티켓 상태:
  - (완료) → Fixed
  - (진행 중) → In Progress
  - (예정) → Open
- 스프린트: 현재 진행 중인 스프린트
- 기획자/디자이너 Feature 아래 Task라도 개발자 담당이면 부모 Feature 컨텍스트 아래 표기 가능
- 기획자/디자이너 담당 Task는 주간업무 개발자 보고 본문에서 제외

**라인 표기 규칙**: 4항(항목 표기 규칙) 참조 — 앞부분 간략 설명, 티켓번호 뒤 YouTrack 티켓 제목 원문 그대로.

## 4. 항목 표기 규칙

KB `DEV2-A-696` 원본 패턴이 source of truth. 가이드와 KB 원본이 다르면 KB 원본을 따른다.

### 4.1 제목 라인 (top-level)

```
* **{제목} ({일정정보, 담당자}** DEV2-xxxx **\[원문제목\])**
```

- 불릿: `*` (하이픈 `-` 아님)
- `**` 짝 2개로 분할 — `**...담당자**` ... **`\[원문제목\])**`
- 원문제목의 대괄호는 `\[` `\]` **escape** (KB 마크다운 렌더링 호환)

### 4.2 본문 라인 (sub-task 또는 단일 본문)

```
  : ({상태}) {간략 설명} ({일정정보}, {담당자} DEV2-yyyy [원문제목])
```

- 2-space indent + `:` + space (불릿 아님)
- 본문 라인 대괄호는 **escape 없이** `[원문제목]` 그대로 (YouTrack 자동 링크 동작)
- 앞 간략 설명은 보고서 흐름상 짧게 요약 (Task 본질만)
- 티켓번호(`DEV2-xxxx`) 뒤에는 YouTrack 티켓 제목을 **수정 없이 그대로** 기재 (대괄호 prefix `[서비스][직군]` 포함)

### 4.3 Feature 하위가 없거나 단일 Task인 경우

본문 라인을 **반드시 작성**하며, 본문 라인의 티켓 정보(`DEV2-xxxx [원문제목]`)는 **제목과 동일**하게 반복한다.

**예시 (단일 본문 — 동일 티켓 정보 반복)**:

```
* **만권당 5월 이벤트 (5월의 책) (5/13, 조은흠** DEV2-5259 **\[만권당\]\[개발\] 5월 이벤트 (5월의 책))**
  : (완료) 5월의 책 디자인/개발 일정 (5/13, 조은흠 DEV2-5259 [만권당][개발] 5월 이벤트 (5월의 책))
```

**예시 (다중 sub-task — 각자 자체 티켓 정보)**:

```
* **\[AASM\] IAM Access Key → Node Role + Self-Assume 마이그레이션 (5/15, 김정민** DEV2-6223 **\[AASM\] IAM Access Key → Node Role + Self-Assume 마이그레이션)**
  : (완료) S3 클라이언트 빌더 신설 + 진입점 제한 (5/15, 김정민 DEV2-6225 [AASM] S3 클라이언트 빌더 신설 + 진입점 제한)
  : (완료) S3 연산 모듈 시그니처 일괄 변경 (5/15, 김정민 DEV2-6226 [AASM] S3 연산 모듈 시그니처 일괄 변경)
```

### 4.4 일자정보 포맷 (3항과 동일)

- 진행 중 → `~완료예상일`
- 예정 → `시작예정일~`
- 완료 → `완료일`
- 백로그(보류) → 일자 생략 가능
- 지연 → `~~기존목표~~ ~수정목표`, 제목 뒤 ` - 지연` 표시, 본문에 지연 사유 기재

**방향 고정 규칙 (반복 오류)**: 진행중 항목은 **항상 `~M/D`(완료 경계)**, 계획(미착수) 항목은 **항상 `M/D~`(시작 경계)**로 쓴다. 진행중 항목에 `M/D~`를 쓰지 않는다. 근거 날짜가 부족해도 방향을 바꾸지 말고 §4.5의 상태별 fallback으로 채운다. 유일한 예외는 §4.5의 월 단위 운영 umbrella다.

### 4.5 예정일 선택과 fallback

대상 월 스프린트에서 아직 시작되지 않았거나 종료되지 않은 티켓(`Open`/`Reopened`/`In Progress`)은 각 Feature·Task 코멘트에 기록된 예정일을 일정정보의 기본값으로 사용한다. 완료 티켓의 완료일은 이 규칙의 대상이 아니다.

**코멘트 해석**:

- 코멘트는 자유 형식이므로 제목·본문·목록 위치나 특정 양식에 한정하지 않고 문맥상 업무 일정인지 판별한다.
- `Open`/`Reopened`는 시작·착수·진행 예정일을, `In Progress`는 완료·종료·마감 목표일을 선택한다.
- 행사 기간, 배포일, 다음 정기 변경일처럼 티켓 작업의 시작·완료와 무관한 날짜는 제외한다.
- 취소선 처리된 과거 일정은 무시하고, `updated`(없으면 `created`) 기준 최신 코멘트의 유효한 일정 표현을 우선한다.
- 범위는 미착수 티켓이면 시작 경계, 진행중 티켓이면 종료 경계를 사용한다. 상대 날짜는 코멘트 작성 시각의 KST 기준으로 한 날짜가 확정될 때만 변환한다.
- 추출한 날짜는 `M/D`로 정규화한 뒤 미착수는 `M/D~`, 진행중은 `~M/D`로 표시한다.

**Feature·Task fallback**:

| Feature 코멘트 명시일 | Task 코멘트 명시일 | Feature 일정정보 | Task 일정정보 |
|---|---|---|---|
| 있음 | 있음 | Feature 자체 날짜 | Task 자체 날짜 |
| 있음 | 없음 | Feature 자체 날짜 | Feature 명시일 상속 |
| 없음 | 하나 이상 있음 | 대상 Task 명시일 중 가장 빠른 날짜 | 날짜가 있는 Task는 자체 날짜 |
| 없음 | 없음 | 상태별 fallback (아래) | 상태별 fallback (아래) |

- 일부 Task에만 날짜가 있으면 Feature는 기록된 Task 날짜 중 최솟값을 사용하지만, 날짜가 없는 다른 Task는 상태별 fallback으로 표시한다.
- Task에서 롤업한 Feature 파생 날짜는 다른 Task로 다시 상속하지 않는다. Task는 Feature 코멘트의 **명시일**만 상속할 수 있다.

**일정정보 우선순위 — 미착수(`Open`/`Reopened`)**:

1. **코멘트 명시일** — 자체 코멘트 시작예정일 > Feature 명시일 상속 (위 표) → `M/D~`
2. **착수일 fallback** — 착수일 = `State`가 `In Progress`로 전환된 시각(YouTrack `activities` API의 `CustomFieldCategory` State 변경), 없으면 `created` → `M/D~`
3. **미기록** — 근거가 없거나 `created`가 대상 월 밖이라 시작예정일 근거로 부적절하면 임의 추정 없이 `<font color="red">미기록</font>`

**일정정보 우선순위 — 진행중(`In Progress`)**:

1. **코멘트 명시일** — 자체 코멘트 완료·종료·마감 목표일 > Feature 명시 완료일 상속 → `~M/D`
2. **스프린트 종료 fallback** — 완료 목표 코멘트가 없으면 **대상 월 스프린트 종료일**(예: 2026-07 → `~7/31`)을 완료 목표로 쓴다. 동시에 이슈사항에 "완료 목표 코멘트 미기재"로 남겨 보강을 요청한다.
3. **착수일을 완료 목표로 쓰지 않는다.** 진행중 항목에 `M/D~`(시작 경계)를 표기하는 것은 오류이다. 착수일 fallback은 미착수 항목 전용이다.

- **예외 — 월 단위 운영 umbrella**: 제목이 `{서비스} N월 운영` 형태로 그 달 전체가 작업 기간인 umbrella Feature는 완료 목표가 아닌 운영 기간을 뜻하므로 운영 시작일 `M/D~`를 유지한다.
- 착수일 조회는 `GET /api/issues/{id}/activities?categories=CustomFieldCategory&fields=timestamp,field(name),added(name)`에서 `field.name`이 `State` 또는 로컬라이즈된 `상태`이고 `added`에 `In Progress`가 포함된 최초 항목의 `timestamp`를 사용한다.

## 4-B. 보고 포맷 개편 (2026-07~)

DEV2-A-694(조윤주) 포맷을 차용해 가독성을 높인 신규 표준. §4.1~4.4의 제목 2회 반복 패턴을 대체한다. 기존 KB `DEV2-A-696`가 이 포맷으로 이관되기 전까지 초안 작성은 이 절을 우선한다.

### 4-B.1 이번 주 요약 (섹션 최상단)

모든 상태 섹션 앞에 `## 이번 주 요약`을 둔다.

```
## 이번 주 요약

* 계획 N건 · 진행중 N건 · 완료 N건 (YYYY/MM/DD 상태 동기화 기준)

| 담당자 | 계획 | 진행중 | 완료 |
|---|---|---|---|
| 김정민 | .. | .. | .. |
| ...   | .. | .. | .. |

* [서비스] 핵심 변동 하이라이트 (완료·착수·지연·리스크) 5~6줄
```

- 건수 라인 = top-level Feature/Epic 기준. 담당자 표는 dev role 정직원만(`policies/team-members.md`).
- 하이라이트는 서비스 앞머리로 시작하고, 상태 후퇴·부모 하위 불일치·미기록 등 이슈는 "이슈사항 참조"로 연결한다.

### 4-B.1.1 이번 주 핵심목표 (KB DEV2-A-1351 취합)

주간별 핵심목표는 별도 KB 트리 [DEV2-A-1351](https://aladincommunication.youtrack.cloud/articles/DEV2-A-1351/7KO86rCE7JeF66y0IO2VteyLrCDrqqntkZw)(주간업무 핵심 목표)에 담당자별로 취합된다. 보고서에는 `## 이번 주 요약` **바로 다음**에 `## 이번 주 핵심목표`를 둔다.

운영 원칙(개수·산출물 증명·미달성 결과 처리)은 [주간 핵심 목표 운영 정책](./weekly-goal-policy.md)이 SoT다. 2026-08-03 주차부터 담당자별 **2개**(도입 주 2026.07.5W는 3개 기준, 1~4개 관측).

```
## 이번 주 핵심목표

**{담당자}**

1. {핵심목표 원문} — DEV2-xxxx
2. {핵심목표 원문} — DEV2-xxxx, DEV2-yyyy
```

- **주차 문서 탐색**: `DEV2-A-1351`의 `childArticles`에서 대상 주차 문서(`YYYY.MM.NW`)를 찾는다. 없으면 최신 주차 문서를 쓰고 그 사실을 이슈사항에 남긴다.
- **원문 그대로 옮긴다**: 담당자 구분·항목 순서·문구·티켓 ID를 KB 원문 그대로 유지한다. 묶거나 재정렬하지 않는다.
- **보강 금지**: 상태·일정정보·`티켓 미발행` 같은 주석을 붙이지 않는다. 출처 인용 문구, 필터 제외 사유 각주도 넣지 않는다. 티켓 번호가 없는 항목은 원문대로 번호 없이 둔다.
- **필터와의 관계**: 핵심목표는 취합 그대로 싣고, 상태 섹션(계획/진행중/완료) 편입 여부만 §1 기록 대상 필터로 판단한다.
- **중복**: 핵심목표 섹션과 상태 섹션에 같은 ID가 함께 등장하는 것은 허용한다(§1 중복 제거는 같은 레벨에만 적용).
- **주차 번호 불일치**: KB 핵심목표는 해당 월 1일 기준 주차(예: 7/27~31 = `2026.07.5W`), vault 주간보고 파일명은 월 첫 월요일 기준 주차(예: `2026-07-4W`)를 쓴다. 서로 다를 수 있으므로 출처 인용 시 KB 원문 주차 표기를 그대로 적고, 파일명 규칙은 바꾸지 않는다.

### 4-B.2 서비스 그룹핑

각 상태 섹션(계획/진행중/완료) 내부를 서비스별 `**서비스명**` bold 소제목으로 묶는다.

- 서비스 그룹명은 **한글 통일**: 바자르, 나루, 만권당, 투비컨티뉴드, 스토어프론트, 근태관리, 음반, 디자인시스템 등.
- 단, 티켓 **원문 제목**의 대괄호 prefix(`\[Bazaar Admin\]`, `\[Naru\]` 등)는 원문 보존 — 그대로 둔다.
- 한 서비스에 항목이 여럿이면 담당자 순으로 정렬한다.

### 4-B.3 라인 단순화

**제목 라인** (§4.1 제목 2회 반복 대체):

```
* **\[서비스\] 제목** ({일정정보}, {담당자}, DEV2-xxxx)
```

- 원문제목을 한 번만 쓴다. `**...담당자**` + `**\[원문제목\])**`의 이중 bold 분할과 제목 반복을 제거한다.
- 티켓ID는 메타 괄호 끝에 `DEV2-xxxx`로 둔다. YouTrack/KB는 ID만으로 자동 링크가 걸린다(DEV2-A-694에서 실증).
- Feature(하위 Task 없음)는 제목 라인 하나로 끝낸다.
- **최상위 Task**(Type=Task가 하위 Feature 없이 top-level로 오는 경우)는 제목과 **동일한 하위 라인 1개**를 반드시 생성한다. 상태별 말머리를 붙이고 §4-B.3 본문 규칙(완료만 날짜)을 따른다:

```
* **\[서비스\] {제목}** ({일정정보}, {담당자}, DEV2-xxxx)
  : (예정) {제목} ({담당자}, DEV2-xxxx)          # Open — 날짜 생략
  : (진행 중) {제목} ({담당자}, DEV2-xxxx)        # In Progress — 날짜 생략
  : (완료) {제목} ({완료일}, {담당자}, DEV2-xxxx)  # Fixed/Closed/Verified — 완료일 유지
```

**본문(하위 Task) 라인**:

```
  : ({상태}) {간략 설명} ({담당자}, DEV2-yyyy)          # (예정)/(진행 중)
  : (완료) {간략 설명} ({완료일}, {담당자}, DEV2-yyyy)   # (완료)만 날짜
```

- **하위 Task 날짜는 (완료)만 표시**한다. (예정)/(진행 중) 하위는 `({담당자}, DEV2-yyyy)`로 날짜를 생략한다 — feature 일정과 중복되고 미기록 노이즈만 늘기 때문. Feature 제목 라인의 일정정보는 그대로 둔다.
- 하위 정렬 권장: (진행 중) → (예정) → (완료).

### 4-B.4 이슈사항 활용

상태 후퇴(진행중→Open), 부모-하위 상태 불일치, 완료 목표 경과, 일정 미기록, 삭제 티켓 등 동기화에서 감지한 사항을 `## **이슈사항**`에 담당자·티켓ID와 함께 기록한다.

### 4-B.5 이월 검토 표시

코멘트에 이월·범위 제외 **결정이 명시**되었지만 상태가 아직 `Open`(Backlog 전환 전)인 항목은 **본문에서 빼지 않는다**. 계획 항목에 그대로 두고 검토·제외 판단이 가능하도록 마커를 붙인다.

```
* **\[서비스\] 제목** ({이월시점}~, {담당자}, DEV2-xxxx) - {대상} 이월 검토
  : (예정) {간략 설명} ({담당자}, DEV2-yyyy)
```

- **마커**: 제목 라인 끝에 ` - {대상} 이월 검토`를 붙인다. 대상은 코멘트 결정 문구 그대로 쓴다 (`8월 이월 검토`, `4분기 이월 검토`).
- **일정정보**: 이월 시점을 시작 경계로 `{N}월~` 또는 `{N}분기~`로 쓴다. 월·분기만 확정된 경우 `M/D` 정규화를 강제하지 않는다. 지나간 원래 시작예정일을 그대로 두지 않는다.
- **하위 Task**: `(예정)` 말머리를 유지한다.
- **이슈사항 기록**: 대상 목록·근거 코멘트 날짜·승인 대기 여부(예: "Backlog 전환은 팀장 사전 승인 후")를 `## **이슈사항**`에 모아 최종 제외 판단을 사용자가 하도록 남긴다.
- **제외 시점**: 실제로 `Backlog`로 전환된 뒤부터 본문에서 제외한다(§1 제외 규칙). 결정 코멘트만 있는 단계에서 미리 빼면 검토 기회가 사라진다.
